# v1.6.9 优化方案

## 1. 方案定位

v1.6.9 的目标不是把所有任务无条件改成最大并发，而是把“存储介质静态限速”改为“有效资源约束 + 真实 benchmark 选择”。

核心原则：

1. HDD、SSD、同设备和跨设备只作为调优维度、风险标签和实测上下文，不再直接截断 worker 候选集合。
2. 内存、cgroup/affinity、文件描述符、Zarr 物理 chunk ownership、临时空间和原子发布仍是硬安全边界。
3. 所有后端使用同一份有效资源快照和同一套 worker/目标函数语义。
4. 更高并发必须通过实测吞吐、耐久吞吐、RSS、失败原因和方差决定，而不是通过固定经验值决定。
5. 调优过程和最终选择理由必须进入 manifest 与 events.jsonl，能够解释“为什么选择这个计划”。

本方案基于 v1.6.8 的代码调查、运行日志和一次真实 GOSIF-GPP 转换运行记录；本文件是实施设计，不代表 v1.6.9 代码已经完成。

## 2. v1.6.8 基线与问题

### 2.1 真实运行基线

成功任务：`20260810-142100-c96185c02da9428d9b383ebd7f0a0a1e`

- 输入：外接 HDD / NTFS；临时目录：SSD；输出：HDD。
- CPU：6 physical / 12 logical；有效 worker 上限：6。
- 有效可用内存：约 24.7 GiB。
- 转换自动调优测试了 1、2、3、4、6 worker，最终选择 2 worker。
- 转换 writer 指标：34,974,720,000 logical bytes、989.7 s、33.7 MiB/s、RSS 约 1.48 GiB。
- 重采样计划：`tile=1024`、`time_block=16`、`space_workers=3`、`compute_workers=2`。
- 重采样指标：308.9 s；逻辑输出约 8.74 GB；物理输出约 2.67 GB；数学验证和语义验证通过。
- 最终化阶段因布局兼容而跳过，直接发布最终 Zarr。

第一次任务在处理前因临时根目录无写权限失败，说明当前缺少临时目录可写性预检。

### 2.2 代码层面的静态限制

| 模块 | 当前限制 | v1.6.9 处理 |
|---|---|---|
| 源检查 | HDD + 大量小文件时最多 2 个检查 worker | 取消静态 HDD 上限，由 metadata I/O benchmark 和有效资源决定 |
| 转换初始计划 | many-small / balanced 根据同设备和 rotational media 限制到 2/3/4 worker | 不删除候选；存储只作为 benchmark profile |
| 转换调优 | 已有候选实测，但未统一使用 effective CPU/resource snapshot | 统一资源契约，记录全部候选和选择理由 |
| 重采样 | 主要按 CPU 和内存估算，未实测空间并发 | 增加 space/compute 候选实测，保留内存安全检查 |
| 重分块 | network/FUSE、HDD、同设备硬编码 2/3/4 worker 上限 | 移除静态上限，stage 1/stage 2 分别实测 |
| 独立 rechunk CLI | 默认 worker 可能固定为 4，绕过完整 auto tuning | 默认改为 `auto` |
| raw validation smoke | 固定 `auto_tune=False`、`max_workers=2` | 标注为安全 smoke；增加可选的 tuning 代表性模式 |
| Pipeline | storage override 主要传给重分块，未贯通转换和检查 | 贯通所有后端，manifest 记录解析结果 |
| Manifest | 记录最终计划多，记录候选 evidence 少 | 建议升级 schema 6，保存候选、资源、选择和阶段指标 |

## 3. 目标架构

目标数据流：

```text
入口与源数据
    -> 资源快照 / 存储 profile / 临时目录预检
    -> 统一 policy normalizer
    -> benchmark orchestrator 生成候选并实测
    -> objective selector 选择 speed / balanced / compact 计划
    -> inspection / conversion / resampling / rechunk 执行
    -> safety guard + staging + validation
    -> atomic publication
    -> manifest / events.jsonl / tuning evidence
```

配套图纸：`Architecture/architecture-v1.6.9-optimization.drawio`

## 4. 详细实施方案

### P0-A：建立统一资源契约

新增统一的有效资源对象，所有后端 planner 和 tuner 都接收同一实例：

```text
EffectiveResourceBudget
  cpu_physical
  cpu_logical
  cpu_effective          # affinity/cgroup 后的可用 CPU
  memory_available_bytes
  memory_budget_bytes
  fd_soft_limit
  worker_ceiling
  source_storage_profile
  temporary_storage_profile
  output_storage_profile
  same_device_roles
```

要求：

- 不再在 conversion planner、resampling autotune、rechunk autotune 中分别调用不同的 CPU 发现逻辑。
- `FAST_NC_ZARR_THREADS_PER_WORKER` 继续作为显式线程逃生开关，但默认每 worker 一个 native thread。
- 所有进程池继续使用 `spawn`。
- 资源快照必须包含解析前值、解析后值和限制来源，便于解释最终 worker ceiling。

### P0-B：将存储从硬限制改为 benchmark context

删除或重构以下静态逻辑：

- inspection 的 rotational HDD `max_workers=2`；
- conversion planner 中 `same_rotational` 对 2/3 worker 的截断；
- rechunk `_parallel_workers()` 中 HDD、network/FUSE、同设备的固定 2/3/4 上限；
- 独立 rechunk CLI 的固定默认 worker。

新的规则：

- 候选范围原则上为 `1..worker_ceiling`；
- network/FUSE 仍可在 benchmark 失败、随机 I/O 失控或空间安全不足时动态拒绝候选，但不能仅凭介质类型提前拒绝；
- storage profile 参与候选标签、样本分层、耐久吞吐评估和报告，不参与静态 worker cap；
- 同设备场景必须在启动时单独检查可用空间、临时峰值和输出覆盖风险。

### P0-C：统一 benchmark orchestrator

为 conversion、resampling、rechunk 建立相同的候选生命周期：

1. 生成候选 worker、batch、tile/time block、codec 组合。
2. 按 begin/middle/end 或代表性空间窗口抽样。
3. 先做内存和 ownership 静态淘汰。
4. 在真实目标文件系统上执行受限样本。
5. 采集 logical throughput、durable throughput、RSS、CPU、读写吞吐、压缩率、失败分类和方差。
6. 不因一个低并发候选失败而无条件阻断更高并发候选；只有明确的 OOM、空间不足或结构性错误才停止同一候选族。
7. 交给统一 selector 选择最终计划。

建议候选默认包含所有 `1..N` worker，而不是只包含 1、2、4、N；这样能识别 HDD/SSD 上的非单调拐点。

### P0-D：统一选择目标

新增显式调优目标：

- `speed`：优先最大 logical/durable throughput；在吞吐差距不超过约 5% 时偏向更高 worker。
- `balanced`：综合吞吐、耐久吞吐、RSS、压缩率和失败风险。
- `compact`：优先压缩率和资源占用。

selector 必须写入：

```text
selected_candidate_id
selection_objective
near_best_threshold
rejected_candidates
rejection_reasons
confidence
```

默认保持 `balanced`，对明确要求最大速度的任务提供 `speed`。不允许用“更保守”覆盖用户显式的 speed 目标，除非候选触及硬安全边界。

### P0-E：各后端落地规则

#### 源检查

- metadata worker 候选由 `1..effective worker ceiling` 生成。
- 大量小文件不再直接限制到 2；通过 metadata 读取 benchmark 选择。
- 保留文件句柄、连接数和源结构一致性保护。

#### 转换

- `initial_plan` 不再删除机械盘候选。
- 调优和正式写入使用相同的资源快照、存储 profile 和 worker ceiling。
- fixed layout、filename mode、complete mode 统一走同一候选生成接口。
- 继续保持一个源 chunk 一次读取、Zarr codec pipeline 批量写入和 staging 发布语义。

#### 重采样

- 新增 `space_workers`、`compute_workers`、`tile_size`、`time_block` 联合候选。
- xESMF weight 构建、源窗口读取、重采样计算、写入分别统计耗时。
- 内存估算明确拆分 `per_worker_peak_bytes` 和 `aggregate_parallel_peak_bytes`，避免当前 metrics 中的重复乘 worker 问题。
- 对相同网格 no-op 继续保持，不因 speed mode 强制重采样。

#### 重分块与重压缩

- stage 1、stage 2 分开 benchmark，不使用同一个 worker 上限。
- stage 1 以源 chunk ownership 和读取一次为约束。
- stage 2 以目标物理 chunk 对齐、codec buffer、内存预算为约束。
- 真实 benchmark 允许测试到 effective ceiling；只有动态失败或硬预算违规才降级。

### P0-F：预检、发布和恢复

任务开始前完成：

- 临时目录创建和写入测试；
- 输出目录写入测试；
- 同文件系统 UUID 检查；
- 临时峰值和最终输出容量检查；
- 覆盖目标可识别性检查。

失败必须在真正处理前给出明确错误，不留下半初始化任务目录。

现有 staging、校验、备份和原子发布语义保持不变。

### P0-G：manifest 与可观测性

建议将 manifest schema 从 5 升级到 6，增加：

```text
resource_budget
storage_profiles
preflight
candidate_trials
selection
resolved_plans
stage_metrics
worker_memory_semantics
```

每个阶段至少记录：

- requested workers 与 resolved workers；
- worker ceiling 来源；
- 调优候选和被淘汰原因；
- phase wall time；
- logical/physical throughput；
- CPU、RSS、读写吞吐；
- staging、validation、publication 状态。

v5 manifest 不应被静默当作 v6 解释；恢复入口需要明确报告版本不兼容或提供一次性显式迁移。

## 5. 分阶段交付

### v1.6.9.0：资源与观测基础

- 统一 `EffectiveResourceBudget`。
- 临时目录写入预检。
- manifest schema 6。
- 修正 resampling memory metrics 命名和计算。
- 不改变已有执行结果选择规则，只增加 evidence。

### v1.6.9.1：移除静态 worker cap

- inspection、conversion、rechunk 移除介质类型静态上限。
- rechunk CLI 默认进入 auto。
- storage profile 只保留为 benchmark context。
- 增加 HDD/SSD/同设备单元测试。

### v1.6.9.2：统一实测选择

- 引入 benchmark orchestrator 和 selector。
- 增加 speed/balanced/compact。
- resampling 增加 space/compute 联合候选。
- 修复低并发候选失败导致高并发候选不执行的问题。

### v1.6.9.3：真实数据验证

- 使用固定 GOSIF-GPP 数据做 1/2/3/4/5/6 worker A/B。
- 覆盖临时 SSD → 输出 HDD、临时 HDD → 输出 HDD、同设备场景。
- 比较 wall time、durable throughput、RSS、磁盘吞吐和校验结果。
- 根据实测结果决定默认目标和 near-best 阈值。

## 6. 验收标准

### 功能和安全

- auto 模式候选范围可达到 effective worker ceiling，不再因 HDD/同设备类型被静态截断。
- 所有后端最终计划、候选和选择理由可从 manifest 复现。
- 临时目录无权限时在处理前失败。
- 内存峰值不超过解析后的预算；Zarr chunk ownership 不重叠。
- 取消、异常和校验失败不会发布 staging 结果。
- 现有 Zarr v3、填充值、逐值校验、时间映射和原子发布测试继续通过。

### 性能

- 相同数据、范围、chunks、codec 和文件系统下，speed 目标选择实测最快候选。
- balanced 目标不因盲目追求最高 worker 造成明显 RSS 或 durable throughput 回退。
- GOSIF-GPP 基线运行的 wall time、写放大和验证结果可与 v1.6.8 逐项对比；性能结论以重复 A/B 的中位数为准，不能依据单次 HDD 缓存状态判断。

### 可观测性

- 日志中显示每个阶段的 requested/resolved worker、effective ceiling 和选择理由。
- events.jsonl 能区分 tuning、execution、validation、publication 阶段。
- manifest 中能区分 per-worker peak 与 aggregate parallel peak。

## 7. 不在本次范围内

- 不改变 Zarr v3 输出格式、`time/lat/lon` 规范和原子发布协议。
- 不为了提高 CPU 利用率取消源 chunk ownership、内存预算或取消响应机制。
- 不通过盲目增加线程数解决 xESMF 权重构建瓶颈；native thread 数仍需由 benchmark 决定。
- 不把单次运行的 HDD 缓存命中结果固化为全局默认值。
