# v1.7.0 Rust 混合重构初步方案

## 1. 方案状态

- 当前版本：v1.6.9
- 工作分支：`refactor/v1.7.0-rust`
- 方案性质：初步设计，不改变 v1.6.9 主分支行为
- 推荐路线：Python 产品层 + Rust 性能核心 + Python fallback

v1.7.0 不进行一次性全量重写。Rust 先替换具有明确输入输出边界、可通过 Zarr v3 交叉校验、且确实存在 Python 调度或内存开销的核心路径。xarray、xESMF 和 PySide6 暂时保留。

当前进度：P0 已完成，P1 正在实现 Zarr v3 元数据读取、固定数值 dtype 的 chunk/region 读写和 Python/Rust 交叉验证。Rust backend 仍未接入现有 Pipeline 默认执行路径。

## 2. 当前基线

项目当前由 Pixi 管理 Python 3.13 环境，核心依赖包括：

- xarray、Dask、NumPy、Zarr v3、numcodecs；
- netCDF4、h5netcdf、GDAL、rasterio、rioxarray；
- xESMF/ESMF；
- PySide6、pyqtgraph；
- psutil。

当前功能边界：

1. NetCDF/HDF/TIFF 目录转换为 Zarr v3；
2. 完整时间维度和文件名时间模式；
3. HDF-EOS 网格元数据恢复；
4. 范围裁剪、变量筛选、填充值和缩放处理；
5. Zarr v3 重采样、重分块、重压缩；
6. Pipeline 计划、恢复、manifest schema 6、events.jsonl 和原子发布；
7. PySide6 GUI 与 CLI 共用 `application.services`。

当前 v1.6.9 的安全约束必须保持：

- Zarr v3 输出协议不变；
- `time/lat/lon` 规范不变；
- 物理 chunk ownership 不重叠；
- 有效 CPU、内存、文件描述符和临时空间预算仍为硬边界；
- staging 校验成功前不发布最终输出；
- 取消、异常和校验失败不能产生伪成功产品。

## 3. v1.7.0 目标

### 3.1 目标

- 在不破坏 Python API、CLI 和 GUI 的前提下引入 Rust backend；
- 降低 Zarr chunk 读写、重分块和重压缩的 Python 调度开销；
- 使 worker、chunk region、资源预算和 benchmark 逻辑拥有明确的类型边界；
- 保持 Python backend 可用，支持逐任务回退；
- 为未来 Rust 原生 CLI 和跨平台发行建立 Cargo workspace；
- 用真实数据和固定文件系统对比 Python/Rust backend，而不是用语言直觉判断性能。

### 3.2 非目标

v1.7.0 不做以下事情：

- 不立即替换 xarray 数据模型；
- 不立即重写 xESMF/ESMF；
- 不立即重写 PySide6 GUI；
- 不改变 Zarr v3、manifest schema 6、CLI 参数语义和 Python 服务入口；
- 不删除 Python fallback；
- 不为了追求 Rust 化而修改科学计算结果或放宽内存安全边界；
- 不在没有跨语言黄金数据验证前切换默认 backend。

## 4. 目标架构

```text
PySide6 GUI / CLI
        |
        v
application.services
        |
        v
统一配置、计划、manifest 和错误协议
        |
        +-----------------------+
        |                       |
        v                       v
Python backend            Rust native backend
(xarray/xESMF/Dask)       (PyO3 + zarrs)
        |                       |
        +-----------+-----------+
                    |
                    v
        staging Zarr v3 / validation / atomic publish
                    |
                    v
              最终产品与 metrics
```

Rust backend 通过 PyO3 暴露为可选扩展模块：

```text
fast_nc_zarr._native
```

Python 负责：

- 参数解析；
- 服务层和 GUI；
- xarray 数据模型；
- xESMF 重采样；
- 复杂格式 fallback；
- manifest 兼容和任务恢复。

Rust 负责第一阶段：

- Zarr v3 chunk store；
- codec pipeline；
- 重分块和重压缩；
- chunk region 和 ownership 计算；
- worker 调度；
- benchmark 核心循环；
- 可选的标准 NetCDF/TIFF 快路径。


建议第一版 Rust 依赖：

- `zarrs`：Zarr v3 存储和 codec；
- `ndarray`：受边界约束的数值 buffer；
- `rayon` 或受控线程池：并行执行；
- `serde`/`serde_json`：计划、metrics 和 manifest 协议；
- `thiserror`：稳定错误分类；
- `pyo3` + `numpy`：Python 扩展和受控 buffer 交换；
- `maturin`：开发安装和 wheel 构建；
- `netcdf`、`hdf5-metno`、`gdal`：第二阶段按 feature 可选启用。

ESMF 不作为第一阶段 Cargo 依赖。重采样继续使用现有 Python xESMF backend。

## 6. Backend 协议

### 6.1 CLI

保持现有参数不变，新增可选参数：

```text
--engine {auto,python,rust}
```

语义：

- `python`：强制现有实现；
- `rust`：强制 Rust，能力不足时明确报错；
- `auto`：满足能力矩阵时使用 Rust，否则回退 Python。

默认仍为 `auto`，但 v1.7.0 初期只有经过验证的操作才允许自动选择 Rust。

### 6.2 Python 服务层

现有入口保持兼容：

```python
inspect_source(...)
preview_conversion(...)
run_conversion(...)
preview_pipeline(...)
run_pipeline(...)
run_rechunk(...)
```

服务层增加 backend 选择和能力报告，不把 PyO3 类型泄露到公共 API：

```python
BackendCapability(
    name="rust",
    operation="rechunk",
    supported=True,
    reason=None,
)
```

### 6.3 Manifest

继续使用 schema 6，并增加 backend 证据字段：

```json
{
  "backend": {
    "requested": "auto",
    "resolved": "rust",
    "fallback": false,
    "fallback_reason": null,
    "protocol_version": 1
  }
}
```

Rust backend 不直接自由修改 manifest。它返回 JSON-safe metrics，由 Python Pipeline 统一写入 manifest 和 `events.jsonl`，避免产生两套持久化语义。

## 7. 分阶段实施

### P0：构建基础，不改变默认行为

交付：

- Cargo workspace；
- Rust/Python CI 构建；
- PyO3 + maturin 开发安装；
- `--engine` 参数和 capability probe；
- Rust 错误分类到 Python 异常的映射；
- 不启用 Rust 执行，只验证构建和协议。

验收：

- `pixi run test` 保持通过；
- `cargo test --workspace` 通过；
- `maturin develop --release` 能导入 `_native`；
- Python 环境没有硬编码本地 Rust target 路径。

### P1：Rust Zarr v3 inspection 和 chunk I/O

交付：

- 读取 Zarr v3 root/array metadata；
- 识别 shape、dtype、chunks、codec 和属性；
- 读取单个 chunk 和 region；
- 写入 staging Zarr；
- Python `zarr`/xarray 可正常打开 Rust 生成的结果；
- Rust 可读取 Python zarr v3 生成的 fixture。

限制：

- 先支持当前项目实际使用的固定数值 dtype；
- 暂不支持复杂对象、变长字符串和非规则网格；
- 暂不切换 Pipeline 默认 backend。

### P2：Rust 重分块和重压缩 backend

优先替换：

1. 等价布局复制；
2. 仅 codec 变化；
3. 单阶段源 chunk → 目标 chunk；
4. 两阶段流式重分块；
5. stage 1/stage 2 独立 worker tuning；
6. durable write、RSS、logical throughput 和失败分类。

保持 Python 侧负责：

- 输入检查；
- 计划生成；
- overwrite 安全检查；
- staging 发布；
- 结果验证和 manifest。

Rust 只执行明确的 `RechunkExecutionPlan`，不自行推断用户意图。

### P3：标准 NetCDF/TIFF 转换快路径

初始支持范围：

- 标准 `time/lat/lon`；
- 三维数值变量；
- 明确的 dtype；
- 明确的 fill/scale 语义；
- 规则网格；
- 无额外复杂维度；
- 输出 Zarr v3。

继续 fallback 的情况：

- HDF-EOS `StructMetadata.0`；
- 非标准维度和复杂时间规则；
- 非数值变量；
- 复杂 CF 引用属性；
- xarray 对齐或广播语义；
- Rust reader 能力报告为不支持的文件。

### P4：评估重采样和 GUI

只有 P1-P3 的正确性和性能稳定后才评估：

- ESMF C/Fortran FFI；
- Rust 原生 weight cache；
- PySide6 保留或改为 Qt/QML；
- 跨平台原生发行。

P4 不是 v1.7.0 的默认交付目标。

## 8. 测试策略

### 8.1 交叉兼容测试

每个 fixture 至少执行：

```text
Python 写入 → Rust 读取
Rust 写入 → Python zarr/xarray 读取
Python backend → Rust backend 结果比较
```

比较内容：

- shape；
- dtype；
- time/lat/lon；
- attributes；
- fill value；
- chunks；
- codec metadata；
- 代表性逐值结果；
- NaN 和缺测值；
- 输出目录结构。

不要求压缩后的物理字节完全相同，但要求解码值和 Zarr 语义一致。

### 8.2 必须覆盖的边界

- 完整时间模式；
- 文件名 DOY 模式；
- 年月日文件名模式；
- 跨文件边界 chunk；
- 空间范围裁剪；
- 变量筛选和重命名；
- `_FillValue`、`missing_value`、scale/offset；
- 空间 chunk 不整除数据 shape；
- codec-only；
- 等价布局复制；
- 取消；
- worker 候选失败；
- 输出目录无权限；
- staging 校验失败；
- overwrite 非 Zarr 目录；
- Rust 能力不足后的 Python fallback。

### 8.3 性能验收

固定以下条件后比较 Python/Rust：

- 相同源数据；
- 相同范围和变量；
- 相同 chunks 和 codec；
- 相同临时、输出文件系统；
- 相同 worker ceiling；
- 至少五次重复运行，以中位数判断。

至少记录：

- wall time；
- logical/durable throughput；
- peak RSS；
- CPU 使用率；
- 物理读写量；
- 压缩比；
- Python 调度耗时；
- fallback 次数和原因。

[建议阈值]：Rust backend 首次正式启用前，不应比 Python backend 慢超过 10%，并应在重分块或 codec-heavy 任务上获得可重复的性能收益。

## 9. 风险和回滚

### 风险

1. `zarrs` 与 Python zarr v3 的 codec/metadata 差异；
2. NetCDF/HDF5/GDAL native library 的 ABI 和发行问题；
3. Rust/Python buffer 转换引入隐式复制；
4. HDF-EOS 和 CF metadata 语义缺失；
5. worker/cancellation 竞争条件；
6. Rust backend 在 Linux 可用，但在其他平台无法构建；
7. xESMF 仍然保留，导致完整产品并非纯 Rust。

### 回滚原则

- 主分支继续保持 v1.6.9；
- Rust 代码只在新分支中开发；
- 每个 backend 通过显式 capability 才能启用；
- Rust 任务失败时保留 staging 和错误事件，不自动伪装成 Python 成功；
- 任意阶段出现数值或 metadata 回归，默认恢复到 Python backend；
- 不删除 Python 实现，直到一个完整版本的真实数据回归通过。

## 10. 第一批实现顺序

建议按以下顺序开始编码：

1. `rust/Cargo.toml` workspace 和 `fast-nc-zarr-model`；
2. Rust/Python backend capability 协议；
3. `zarrs` 打开/读取/写入最小 fixture；
4. codec 和 chunk region 交叉测试；
5. 等价布局复制 backend；
6. codec-only backend；
7. 单阶段重分块；
8. 两阶段重分块和真实 tuning；
9. Pipeline manifest/backend evidence；
10. 标准 NetCDF/TIFF 转换快路径。

在第 8 步以前，不修改 GUI 默认行为，也不接入 xESMF 重采样。

## 11. 决策门

满足以下条件后，才允许将 Rust backend 从显式 opt-in 改为 `auto` 默认候选：

- 所有现有 Python 测试继续通过；
- Rust/Python 交叉 fixture 全部通过；
- manifest 和 events 证据可复现；
- 取消、异常、无权限和 overwrite 安全行为一致；
- 至少一个真实 NetCDF/HDF/TIFF/Zarr 数据集完成重复 A/B；
- 性能收益不是单次 HDD cache 命中造成的假象；
- Rust wheel 或 Pixi 构建在目标平台可重复；
- capability 不支持时 fallback 可解释且不会改变输出语义。

在此之前，v1.7.0 的 Rust backend 仅作为实验性后端，不影响 Python 默认路径。
