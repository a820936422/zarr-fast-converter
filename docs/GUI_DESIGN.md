# Zarr 转换器 GUI 与模块化设计方案

本文档面向当前项目的下一阶段开发：为本地 Zarr 转换器增加 GUI，并把工作流程拆分为数据检查、转换、Zarr 优化和结果校验等模块。Zarr 优化接收已有 Zarr 输入，可以独立于原始数据检查运行。

## 1. 设计目标

用户只需要选择一个源数据目录，系统就应当按照以下顺序工作：

```text
选择源目录
    ↓
数据检查
    ↓
确认数据规则（维度、变量、时间、网格）
    ↓
选择操作参数并生成计划
    ↓
执行转换/重分块/重压缩
    ↓
校验输出并保存运行记录
```

设计目标包括：

- 让用户在真正写数据之前看到完整的数据结构和风险提示；
- 把“源数据如何解释”与“数据如何写入 Zarr”分开；
- 检查结果可以被后续模块复用，不必每次重新扫描全部源文件；
- 长时间任务不会阻塞界面，并且可以查看日志、进度、吞吐率和资源使用情况；
- 失败或取消后不会把一个看起来完整、实际上不可用的 Zarr 当成成功结果；
- GUI 和现有命令行入口共享同一套核心服务和数据模型。

当前项目已经具备不少可复用能力：

| 现有代码 | 可复用能力 | GUI 中的职责 |
|---|---|---|
| `inspection.py` | 文件发现、维度/变量/坐标检查、结构一致性检查 | 数据检查模块的后端 |
| `filename_mode.py` | 从文件名识别 DOY 或 YMD、补齐理论时间轴、检查缺失时间 | 时间规则检查与确认 |
| `selection.py` | 时间、经纬度、变量筛选 | 转换参数校验 |
| `planner.py` / `benchmark.py` | 初始计划、候选计划和自动调参 | 转换计划预览 |
| `engine.py` / `writer.py` | 转换、并发写入、进度和校验 | 转换任务执行 |
| `rechunking/inspection.py` | Zarr v3 元数据和 chunk 检查 | 重分块/重压缩输入检查 |
| `rechunking/planning.py` | 目标 chunk 计算 | 重分块计划预览 |
| `rechunking/compression.py` | 无损压缩方案 | 重压缩参数选择 |
| `rechunking/engine.py` | Zarr v3 重分块和写出 | 重分块/重压缩任务执行 |

## 2. 推荐的总体架构

建议使用 PySide6 构建本地桌面应用。这个项目需要直接访问本地目录、机械硬盘、进程池和 Zarr 目录，桌面应用比浏览器前端更适合第一版。

GUI 不应直接调用 CLI 中的 `input()` 或模拟终端输出，而应增加一层应用服务：

```text
PySide6 GUI
  ├─ 页面、表格、对话框、进度条
  └─ 信号/槽：开始、取消、日志、进度、结果

Application Services
  ├─ InspectionService       数据检查
  ├─ ConversionService       转换
  ├─ RechunkService          重分块
  ├─ CompressionService      重压缩
  ├─ ValidationService       输出校验
  └─ TaskManager             后台任务、取消、日志、状态

Domain Models / Reports
  ├─ InspectionSnapshot
  ├─ OperationConfig
  ├─ PlanReport
  ├─ ProgressEvent
  └─ TaskRecord

现有核心模块
  └─ xarray / rasterio / netCDF4 / Zarr / Dask / ProcessPoolExecutor
```

推荐的后续目录结构：

```text
src/fast_nc_zarr/
├─ application/
│  ├─ inspection_service.py
│  ├─ conversion_service.py
│  ├─ rechunk_service.py
│  ├─ compression_service.py
│  ├─ task_manager.py
│  └─ schemas.py
├─ gui/
│  ├─ app.py
│  ├─ main_window.py
│  ├─ pages/
│  │  ├─ inspection_page.py
│  │  ├─ conversion_page.py
│  │  ├─ zarr_optimize_page.py
│  │  └─ task_page.py
│  └─ widgets/
└─ 现有核心模块...
```

第一阶段也可以不立即移动现有文件，只新增 `application/` 和 `gui/`。等 GUI 运行稳定后，再逐步整理包结构。

## 3. GUI 的主窗口

主窗口建议采用左侧导航、右侧工作区的布局：

```text
┌────────────────────────────────────────────────────────────┐
│ 快速 Zarr 转换器       当前任务：GOSIF-GPP       [帮助]      │
├──────────────┬─────────────────────────────────────────────┤
│ 数据检查     │                                             │
│ 转换         │              当前模块工作区                  │
│ Zarr 优化    │                                             │
│ 任务与日志   │                                             │
├──────────────┴─────────────────────────────────────────────┤
│ 状态：空闲/检查中/运行中/完成       CPU  内存  磁盘吞吐       │
└────────────────────────────────────────────────────────────┘
```

左侧模块应显示状态图标：

- 灰色：尚未运行；
- 蓝色：正在运行；
- 绿色：检查通过或任务成功；
- 黄色：有警告，需要用户确认；
- 红色：检查失败或任务失败。

后续模块在没有有效的上游检查结果时应保持禁用状态。例如，用户没有确认源数据的时间规则时，“转换”按钮不能执行。

## 4. 数据检查模块

数据检查模块是整个 GUI 的入口，也是最重要的模块。它不写出 Zarr，只读取源文件的元数据和少量坐标/样本数据。

### 4.0 时间维度检查必须先行

数据检查页面采用两个阶段：

```text
选择源目录
    ↓
[检查文件时间维度信息]
    ↓
确认文件名/time 字段如何构建完整日期
    ↓
[检查数据结构]
    ↓
变量、空间网格、属性、筛选和转换
```

用户输入原始目录后，转换入口保持禁用；Zarr 优化使用独立的 Zarr 输入，可以直接进入。点击“检查文件时间维度信息”后，后端只做轻量的文件名和首文件元数据检查：

1. 获取目录内支持的文件并按文件名排序；
2. 比较同一数字字段在全部文件中的值，找出变化字段；
3. 读取首个文件的维度、坐标和 `time` 变量属性；
4. 判断 `time` 是完整日期、DOY、带 `since` 基准的数值时间，还是无法自动解释的原始值；
5. 为文件名和 `time` 分别生成“完整时间、年、月、日、DOY”候选项。

确认界面允许用户选择：

| 来源 | 完整时间 | 年 | 月 | 日 | DOY |
|---|---|---|---|---|---|
| 文件名 | 一个文件名字段 | 一个字段 | 一个字段 | 一个字段 | 一个字段 |
| `time` 维度 | 一个 time 字段 | 一个字段 | 一个字段 | 一个字段 | 一个字段 |

可以直接选择完整时间，也可以组合字段。例如：

- `GLASS04B01.V42.A2001001.2020313.hdf`：选择文件名字段 `2001001` 的完整时间；
- `SMrz_2001_GLEAM_v4.2a.nc`：选择 `time` 解码后的完整日期；
- `lai_8-day_0.1_2001.nc`：选择文件名字段 `2001` 作为年、`time=1/9/...` 作为 DOY。

用户点击“确认时间规则并检查数据结构”后，规则会保存到本次检查任务中，后续所有日期统一归一化为 `YYYY-MM-DD`。只有这一步成功，转换页面才会解锁。

### 4.1 输入区

输入区建议包含：

| 控件 | 说明 |
|---|---|
| 源数据目录 | 文件夹选择器，也支持直接粘贴路径 |
| 是否递归扫描 | 对多级目录的数据有效 |
| 源格式 | 默认自动识别，可显示 NetCDF/HDF/TIFF |
| 读取引擎 | 自动、h5netcdf、netCDF4、rasterio |
| 检查进程数 | 默认自动；机械硬盘不能盲目增加并发 |
| 开始检查 | 启动后台检查任务 |
| 停止检查 | 请求安全取消 |

点击“开始检查”后，界面应立即显示阶段性状态，例如：

```text
发现文件：1104 / 1104
读取元数据：732 / 1104
核对坐标网格：进行中
检查时间字段：等待
```

### 4.2 检查内容

检查报告至少应包含以下几组信息。

#### A. 文件概况

- 源目录和是否递归扫描；
- 文件数量、文件后缀、总大小；
- 单文件大小的最小值、中位数、最大值；
- 文件是否可以全部读取；
- 检测到的读取引擎；
- 源盘和目标盘是否为同一设备、是否为机械硬盘；
- 异常文件列表及异常原因。

#### B. 数据形态与维度

用表格展示原始名称和标准名称：

| 角色 | 原始名称 | 标准名称 | 长度 | 是否一维坐标 |
|---|---|---|---:|---|
| 时间 | `time` 或其他 | `time` | 8048 | 是 |
| 纬度 | `latitude` 或 `YDim:*` | `lat` | 1400 | 是 |
| 经度 | `longitude` 或 `XDim:*` | `lon` | 7200 | 是 |

应明确提示：输出 Zarr 始终使用 `time`、`lat`、`lon`，原始名称只用于读取源文件。

同时显示：

- 每个维度的长度；
- 每个变量的维度顺序，例如 `(time, lat, lon)` 或 `(lon, time, lat)`；
- 是否存在额外维度；
- 是否存在标量变量；
- 纬度是否升序/降序；
- 经度范围、分辨率和是否单调；
- 文件之间网格形状、坐标值和投影信息是否一致。

#### C. 变量和属性

变量表建议提供以下列：

| 变量 | 类型 | 维度 | shape | 源 chunk | 逻辑大小 | 关键属性 |
|---|---|---|---|---|---:|---|
| `GPP` | `uint16` | `time,lat,lon` | `24,1400,7200` | `1,1400,7200` | ... | `_FillValue`, `scale_factor`, `units` |

点击变量可以展开查看完整属性 JSON。关键属性应单独突出：

```text
_FillValue
missing_value
scale_factor
add_offset
units
long_name
standard_name
```

属性检查应区分三类结果：

- 所有文件一致；
- 文件之间存在差异，但不影响转换；
- 文件之间存在结构性差异，不能直接合并。

#### D. 时间规则

时间规则必须在检查模块中确定，并形成后续模块使用的唯一配置。时间来源不再是互斥的二选一，而是支持完整字段或字段组合：

1. **完整时间来自文件名**：例如 `GOSIF_GPP_2001001_Mean.tif`；
2. **完整时间来自 `time` 维度**：例如 `days since 2001-01-01`；
3. **文件名和 `time` 组合**：例如文件名提供年，`time` 提供 DOY；
4. **文件名内部组合**：例如文件名提供年、月、日或 DOY 的不同字段。

自动识别后，界面必须让用户确认，而不是只显示“自动模式”。应显示：

```text
时间来源：文件名
模板：年 + DOY
样例文件：GOSIF_GPP_2001001_Mean.tif
识别字段：2001 / 001
归一化时间：2001-01-01
```

时间检查结果统一使用 `YYYY-MM-DD`，包括：

- 实际时间范围；
- 理论时间范围；
- 文件名中解析出的时间；
- 时间间隔；
- 缺失日期；
- 重复日期；
- 不合法日期；
- 用户后续选择的时间范围。

GUI 中的时间范围应使用日期选择器或两个日期输入框，不要求用户输入 Python 列表。内部仍可转换为 `Selection` 所需的边界。

#### E. 完整性与风险

检查完成后给出总的检查结论：

```text
✓ 1104 个文件均可读取
✓ 空间网格一致：1400 × 7200
✓ 变量结构一致：1 个数据变量
⚠ 发现 3 个理论时间缺口，将在转换时写入空值切片
✓ 已确定时间规则：文件名年 + DOY
```

“继续”按钮只在阻断性错误解决后启用。警告必须由用户显式确认，例如“允许缺失时间并写入空切片”。

## 5. 检查结果的数据契约

当前 `Inventory` 是适合内部运行的内存对象，但 GUI 还需要一个可序列化的检查快照。建议新增 `InspectionSnapshot`，不要让 GUI 直接依赖 xarray Dataset 或 NumPy 对象。

建议的快照结构如下：

```json
{
  "schema_version": 1,
  "source": {
    "path": "/data/GOSIF-GPP",
    "recursive": false,
    "format": "tiff",
    "engine": "rasterio",
    "file_count": 1104,
    "total_bytes": 19327352832
  },
  "fingerprint": {
    "algorithm": "path-size-mtime",
    "file_count": 1104,
    "created_at": "2026-08-06T12:00:00+08:00"
  },
  "dimensions": {
    "source": {"time": null, "y": 1400, "x": 7200},
    "canonical": {"time": 1104, "lat": 1400, "lon": 7200}
  },
  "time": {
    "source": "filename",
    "template": "doy",
    "format": "YYYY-MM-DD",
    "start": "2001-01-01",
    "end": "2022-12-31",
    "frequency": "daily",
    "missing": ["2001-01-02"],
    "duplicates": []
  },
  "variables": [],
  "warnings": [],
  "errors": []
}
```

实际实现中不必完全采用此 JSON 形状，但必须满足：

- 能保存并重新加载；
- 不保存不可序列化的 `Path`、NumPy scalar 或 xarray 对象；
- 能判断源目录是否发生变化；
- 能追溯检查时使用的时间规则、维度映射和引擎；
- 能把快照重新转换为核心模块需要的 `Inventory`。

建议将快照保存为用户明确选择的项目工作目录中的 `inspection.json`，而不是散落在源目录中。源目录不能被程序写入任何隐藏文件。

## 6. 转换模块

转换模块只接受“检查通过且已确认”的 `InspectionSnapshot`。

### 6.1 参数分区

界面可以分成四个折叠区。

#### 数据选择

- 时间开始日期、结束日期；
- 纬度最小值、最大值；
- 经度最小值、最大值；
- 变量多选表；
- 显示预计输出 shape 和未压缩逻辑大小。

时间、纬度、经度的当前有效范围应始终显示在输入框旁边。时间显示只使用 `YYYY-MM-DD`，不再要求用户手工写 `[2001-01-01,2022-12-31]`。

#### 变量处理

每个变量显示检查阶段发现的 `_FillValue`、`missing_value`、`scale_factor` 和 `add_offset`，用户可以确认或修改：

- 是否替换填充值；
- 替换后的输出填充值；
- 是否应用缩放因子；
- 输出 dtype 是否保持原类型或转换为浮点型。

这里必须明确显示“填充值按原始值识别，缩放之后再写出”，避免用户误解。

#### 写入计划

- 自动调优开关；
- 调优预算；
- 最大 worker 数；
- 系统保留内存；
- 是否执行写后抽样校验；
- 输出目录和覆盖策略。

点击“预览计划”后展示：

- 采用 file/chunk/dask 哪种策略；
- `time/lat/lon` chunk；
- worker 数；
- 预计输出大小；
- 目标磁盘剩余空间；
- 源盘和目标盘是否相同；
- 计划选择的理由和潜在风险。

#### 确认执行

执行前显示不可逆或耗时操作确认框：

```text
将读取 1104 个文件，预计写出约 8.4 GiB。
输出：/data/result/gosif.zarr
预计耗时：约 18 分钟
是否开始？
```

### 6.2 转换进度

进度不应只显示一个百分比，建议展示：

```text
阶段：正式写入
任务：532 / 1104
总体：48.2%
逻辑吞吐：312 MiB/s
物理写入：96 MiB/s
剩余时间：约 9 分钟
CPU：620%    内存：4.8 GiB    磁盘写入：105 MiB/s
```

自动调优应单独显示候选数量、当前候选、样本进度和最终选择结果，避免用户误以为正式转换已经开始。

## 7. 重分块模块

重分块模块的输入是已经存在的 Zarr v3。进入模块后先调用 `rechunking/inspection.py`，展示：

- Zarr 版本；
- 维度和 shape；
- 每个变量当前 chunk；
- 当前 codec；
- 逻辑大小和物理大小；
- 数据变量是否都包含 `time/lat/lon`。

参数包括：

- 时间连续；
- 空间连续；
- 自定义 `[time, lat, lon]` chunk；
- 目标 chunk 大小 MiB；
- worker 数；
- 是否执行输出校验；
- 输出目录和覆盖策略。

预览结果应复用 `plan_chunks()` 和 `format_plan()` 的信息，同时增加前后对比：

| 项目 | 当前 | 计划后 |
|---|---:|---:|
| `GPP` chunk | `(1, 1400, 7200)` | `(16, 350, 900)` |
| chunk 数 | 1104 | 160 |
| 单 chunk 未压缩大小 | 19.2 MiB | 19.2 MiB |
| 读取方向 | 空间整幅 | 时间+空间块 |

只有计划通过输入检查和剩余空间检查后，才允许执行。

## 8. Zarr 优化模块

当前重分块器已经可以在重分块时同时更换无损 codec，因此 GUI 将重分块和重压缩放在同一个可组合页面中。用户通过两个复选框选择操作：

```text
重分块：改变数据的 chunk 布局
重压缩：保留 chunk 布局，只改变 codec 参数
两者同时选择：一次任务生成一份同时改变 chunk 和 codec 的输出 Zarr
```

两项同时选择时可以指定独立的中间处理目录，例如 SSD。阶段 1 的中间 Zarr
放在该目录中，阶段 2 将最终块直接写入输出目录所在磁盘；校验通过后只保留最终输出，
成功任务会清理中间目录，失败任务则保留临时目录供排查。

未勾选重分块时，页面读取输入 Zarr 的当前 chunk 并锁定 chunk 编辑项。用户选择：

- 不压缩；
- fast；
- balanced；
- maximum；
- 后续可扩展为自定义 codec、level 和 shuffle。

预览中应明确说明：

- 这是无损重压缩；
- 逻辑数据值不应改变；
- 输出物理大小只能估算，实际结果取决于数据内容；
- 仅改变 codec 时不应重新组织逻辑 chunk；
- 输出仍为 Zarr v3。

实现上可以让 `CompressionService` 调用共享的重写执行器，并使用“输入 chunk = 输出 chunk”的 `ChunkPlan`，不必复制一套底层读写算法。

## 9. 任务管理与状态机

所有检查和写入都应被包装成任务，不能在 Qt 主线程中直接执行。

建议状态：

```text
NEW
  → INSPECTING
  → INSPECTED
  → CONFIGURING
  → PLANNED
  → RUNNING
  → VALIDATING
  → SUCCEEDED

INSPECTING / RUNNING / VALIDATING → CANCEL_REQUESTED → CANCELLED
任何阶段 → FAILED
```

每个任务至少记录：

- task id；
- 操作类型；
- 开始/结束时间；
- 输入和输出路径；
- 使用的检查快照版本；
- 完整参数配置；
- 选中的计划；
- 当前阶段和进度；
- 日志文件路径；
- 错误类型、错误消息和 traceback；
- 输出是否通过校验。

建议使用 `QThread` 或 `QThreadPool + QRunnable` 承载任务控制器。实际数据读写仍可使用现有的 `ProcessPoolExecutor`。两层并发不能无限叠加：GUI 任务线程只负责调度，数据 worker 数由现有规划器和内存/磁盘约束决定。

核心服务应提供类似以下接口，而不是依赖终端打印：

```python
inspection = inspection_service.inspect(
    source_config,
    progress=progress_callback,
    cancel_event=cancel_event,
)

plan = conversion_service.preview(
    inspection,
    selection_config,
    conversion_config,
)

result = conversion_service.run(
    inspection,
    selection_config,
    conversion_config,
    progress=progress_callback,
    cancel_event=cancel_event,
)
```

`progress_callback` 应传递结构化事件，而不是让 GUI 解析中文终端文本：

```python
ProgressEvent(
    task_id="...",
    phase="writing",
    completed=532,
    total=1104,
    logical_bytes=..., 
    physical_bytes=..., 
    message="正在写入 GOSIF_GPP_2009017_Mean.tif",
)
```

## 10. 输出安全、取消和恢复

大规模数据转换最容易出现的问题不是界面，而是中断后留下半成品。因此建议统一采用以下策略：

1. 正式输出先写入同一文件系统下的临时 Zarr 目录，例如 `result.zarr.partial-<task_id>`；
2. 写入和抽样校验全部成功后，再在同一文件系统内改名为最终目录；
3. 最终目录存在时默认拒绝覆盖，用户必须明确选择新的目录或允许覆盖；
4. 取消或失败时标记临时目录为不完整，界面提供“删除本次临时输出”或“保留以便诊断”；
5. Zarr 根目录增加运行清单，记录输入快照、参数、计划和校验结果；
6. 只有存在“完成且校验通过”标记的输出，任务历史才显示为成功。

取消应分成两种：

- **安全取消**：当前任务完成后停止后续任务，适合正式写入；
- **立即停止**：终止 worker，速度快但一定可能留下半成品，只能作用于临时输出。

第一版实现安全取消即可。取消按钮不应删除用户已有的 Zarr，也不应自动覆盖普通非空目录。

## 11. 检查结果缓存和失效规则

检查一个包含大量文件的目录可能耗时很久，因此需要缓存。缓存不能只以目录路径作为 key，应至少包含：

- 源目录绝对路径；
- 是否递归；
- 文件名、大小和修改时间摘要；
- 源格式和引擎；
- 维度映射；
- 文件名时间规则；
- 检查器版本和快照 schema 版本。

下列情况发生时必须让快照失效并要求重新检查：

- 文件数量、文件名、大小或修改时间发生变化；
- 改变了源维度映射；
- 改变了文件名时间模板或字段；
- 改变了读取引擎；
- 检查器版本或快照 schema 发生不兼容变化。

只改变转换的时间范围、经纬度范围、变量选择、chunk 或压缩方案时，不需要重新扫描源数据结构。

## 12. 错误展示原则

错误应分为用户可以处理的错误和程序/环境错误：

| 类型 | 示例 | GUI 行为 |
|---|---|---|
| 输入错误 | 目录不存在、没有支持文件 | 在输入控件旁提示，不能开始检查 |
| 结构错误 | 文件维度不一致、时间重复 | 展示异常文件表，要求修复或取消 |
| 规则歧义 | 文件名有两个可能的日期字段 | 展示候选字段，让用户确认 |
| 空间错误 | 经纬度不单调、网格不一致 | 阻止转换并给出具体文件 |
| 空间不足 | 目标盘不足 | 阻止执行，显示估算和可用空间 |
| 运行错误 | worker 退出、读取失败 | 保留日志和临时输出，允许重试 |
| 校验错误 | 输出 shape 或抽样值不符 | 输出标记为失败，不能显示为成功 |

不要只显示“Error in sys.excepthook”或完整 traceback。用户界面先显示可读的原因和解决建议，详细 traceback 放在“查看详细日志”中。

## 13. 推荐的开发顺序

### 阶段一：抽离服务层

- 给现有检查、转换、重分块函数增加结构化返回值；
- 增加统一的 `ProgressEvent`、取消事件和错误对象；
- 为 `Inventory`、Zarr `DatasetInfo` 增加序列化/反序列化；
- 保留当前 CLI，让 CLI 也通过服务层调用。

### 阶段二：先实现数据检查页面

- 目录选择和后台扫描；
- 文件概况、维度、变量、属性、时间、网格和异常表；
- 时间规则确认；
- 保存和加载 `InspectionSnapshot`。

### 阶段三：实现转换页面

- 变量和空间范围选择；
- 日期选择器；
- 转换计划预览；
- 调优、正式写入、校验和实时进度。

### 阶段四：实现重分块和重压缩页面

- Zarr 输入检查；
- chunk 前后对比；
- 共享的输出安全和任务历史；
- codec 方案预览和无损校验。

### 阶段五：完善任务中心

- 运行历史；
- 日志查看；
- 失败重试；
- 临时输出清理；
- 配置保存为可复用模板。

## 14. 第一版 MVP 的范围

第一版不建议一次实现地图预览、远程数据、分布式集群和复杂的工作流编辑器。推荐先完成：

1. PySide6 主窗口和左侧模块导航；
2. 数据检查页面；
3. 源时间/文件名时间规则确认；
4. 转换页面的日期、空间、变量选择；
5. 转换计划预览和后台执行；
6. 重分块页面；
7. 重压缩页面；
8. 任务进度、日志、取消和输出校验；
9. 检查快照和任务记录保存。

完成上述范围后，用户可以清楚地回答三个关键问题：

```text
这个目录里的数据是什么？
程序准备怎样解释和处理它？
输出是否真的完整、可用并通过校验？
```

这三个问题应当成为 GUI 设计的主线。地图预览、更多文件格式和高级调参都可以在此基础上继续增加，而不改变核心数据契约和任务状态机。
