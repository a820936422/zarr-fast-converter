# Fast NC Zarr v1.7.9 后端处理逻辑优化方案

- **目标版本**：v1.7.9
- **基线版本**：v1.7.8
- **文档更新**：2026-08-18
- **关联文档**：[自动优化代码逻辑汇总](auto-optimization-logic-summary.md)、[v1.7.8 后端优化分析](v1.7.8-backend-optimization-analysis.md)、[维护文档](MAINTENANCE.md)

本文档是在自动优化代码逻辑汇总基础上拟订的后端处理逻辑优化方案。核心目标：让程序在不同硬件配置（HDD/SSD/NVMe、内存受限容器、多路服务器）下都能自动逼近“当前硬件条件下的最优吞吐”，同时保持正确性、可恢复性和可观测性。

---

## 1. 目标与原则

### 1.1 目标

1. 建立可复用的硬件画像与性能模型，替代“按介质类别给固定值”的粗粒度判断。
2. 让所有自动调优都有**初始值 + 全范围探索 + 运行期反馈**三层机制：
   - 初始值：快速给出一个合理起点；
   - 全范围探索：调优阶段不因介质类别截断候选；
   - 运行期反馈：正式执行中根据实测吞吐/CPU/磁盘队列/RSS 动态微调。
3. 降低进程池创建销毁、中间 Zarr 多遍读写、线程过订阅等结构性开销。
4. 保持 staging、校验、checkpoint、manifest/event 等可靠性承诺不变。

### 1.2 设计原则

- **初始值不是硬上限**：存储感知只决定“从哪里开始找”，不决定“最多能到多少”。
- **实测驱动**：任何硬件决策最终以真实小样本/真实任务测量为准。
- **可回退**：在线控制器或性能模型失效时回退到确定性初始计划。
- **可观测**：所有自动决策和运行期调整写入 manifest/events，便于复现与审计。

## 2. 核心设计

### 2.1 HardwareProfile（硬件画像）

在现有 `RuntimeResourceSnapshot` 基础上扩展：

- CPU：物理/逻辑核、affinity/cgroup、NUMA 节点、P/E 核分组、L2/L3 cache 大小。
- 内存：总量/可用/cgroup、内存带宽粗测。
- 存储：介质、文件系统、**实测顺序读/写带宽、随机 4K IOPS、磁盘队列深度**、源/临时/输出是否同设备。
- 系统负载：启动时 CPU/IO 占用。
- 持久化：按设备/路径缓存 profile，避免每次启动重复微基准。

接口草案：

```python
@dataclass(frozen=True)
class StorageBenchmark:
    medium: str
    seq_read_mib_s: float
    seq_write_mib_s: float
    rand_read_iops: float
    queue_depth: float
    same_device: bool

@dataclass(frozen=True)
class HardwareProfile:
    cpu: CPUResources
    memory: MemoryResources
    storage: dict[str, StorageBenchmark]  # source/temporary/output
    numa: tuple[tuple[int, ...], ...] | None
    effective_cpus: int
```

### 2.2 WorkloadClassifier（工作负载分类）

在现有 `workload_kind` 基础上增加：

- 计算密度：变量数量、dtype、是否带变换、是否重采样方法（conservative vs nearest）。
- I/O 密度：总字节、文件数、时间点数、压缩比预期。
- 输出形态：直接 Zarr 写、重采样、重分块、pipeline。
- 分类结果用于性能模型与候选剪枝。

### 2.3 PerformanceModel（性能模型）

对每个候选 plan 估算：

```text
T ≈ T_spawn + T_read + T_transform + T_compress + T_write + T_validate
```

- `T_read`：由存储实测带宽、窗口大小、顺序/随机模式决定；
- `T_compress`：由 CPU 核数、codec/level、数据可压缩性决定；
- `T_write`：由目标存储带宽、chunk 大小、staging 设备决定；
- `T_spawn`：由 worker 数与进程池生命周期决定。

模型不要求绝对精确，用于**剪枝候选空间**，让样本调优聚焦在少数有希望的 plan 上。

### 2.4 StorageAwareScheduler（存储感知调度）

- **初始值**：HDD 大文件/均衡初始 4 workers、多小文件 8；network 2/4；SSD/NVMe 保持 CPU 上限。
- **全范围探索**：`candidate_plans` / `worker_candidates` 仍覆盖 `1..worker_ceiling`。
- **执行策略**：
  - HDD：低并发 + 大 chunk + `task_batch≥4` + 文件亲和调度 + 读写阶段分离（源/输出同设备时）；
  - SSD/NVMe：高并发 + 小 chunk + 低压缩；
  - 网络存储：有界并发 + 本地 staging/预取；
  - 源/输出同设备：限制总并发或把 staging 放到不同设备。

### 2.5 OnlineController（在线反馈控制器）

正式执行期间以 1–5 秒粒度采样：

- `achieved_throughput`、`cpu%`、`rss`、`disk_queue/await`；
- 若吞吐停滞且 CPU 低 → 疑似 IO 瓶颈：降低并发 / 增大 chunk / 开启 read-ahead；
- 若 CPU 高且磁盘空闲 → 疑似 CPU 瓶颈：降低压缩等级 / 减少 worker / 增大 batch；
- 若 RSS 接近预算 → 降低 worker / 减小 time_block / 启用 memmap；
- 每次调整写入 manifest/events。

实现范围建议：先只在 `direct_write` 与 `run_resample` 内做“只读监控 + 保守调整”，后续再扩展到 pipeline。

### 2.6 WorkerPool（长驻进程池）

- 提供进程池复用层，跨 `direct_write`、`resample`、`rechunk` 和 pipeline 阶段复用 worker。
- 按 `memory_budget` 限制池大小，空闲时释放。
- 减少 spawn 开销，尤其对短任务和多阶段 pipeline。

### 2.7 PipelineFusion（流水线融合）

- 对 `direct_compatible` 且无需 checkpoint 的路径，将转换/重采样/重分块改为**单遍流式**：
  - 转换 worker 在内存中按目标 chunk 产出；
  - 直接交给重采样/重分块逻辑；
  - 避免中间 Zarr 全量写读。
- 保留 staging、原子发布、失败清理；融合时记录 `write_amplification` 下降量。

### 2.8 BackendSelection（后端选择）

- 维持 capability matrix + `backend=auto` 显式 fallback；
- 扩大 native 覆盖（int16、HDF-EOS、更多重采样方法）以降低 Python 开销；
- native 路径同样接入资源预算与在线反馈。

### 2.9 Observability（可观测性）

- manifest 增加 `hardware_profile`、`performance_model`、`online_adjustments`；
- 提供 `performance-mode` 预设：`balanced` / `max-throughput` / `low-memory` / `hdd-safe` / `ssd-max`；
- 暴露 `pixi run benchmark-hardware-profile` 等诊断命令。

## 4. 风险与回退

- **不要过度工程**：在线控制器默认保守，失败时回退到确定性初始 plan。
- **HDD 行为差异大**：初始值只作起点，最终由实测决定；不在非实测路径做硬编码。
- **流水线融合可能破坏 checkpoint/恢复**：只对可安全融合的路径开启，保留 staging 和 manifest。
- **在线调整会导致非确定性**：所有调整必须写入事件/manifest，便于复现。
- **长驻 worker 池增加常驻内存**：需按 `memory_budget` 限制池大小，空闲时释放。
- **硬件微基准耗时**：应缓存结果，并允许用户跳过（环境变量或配置）。
