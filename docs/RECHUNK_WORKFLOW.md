# Zarr 快速重分块与重压缩工作流

本文档定义第二个模块的范围和流程。它接收第一个模块生成的 Zarr v3，重新组织
chunk 布局，并可在同一次扫描中更换无损压缩 codec。

## 1. 模块边界

重分块器与源数据转换器分开运行：

~~~text
convert.py   源 NetCDF/HDF/TIFF -> Zarr v3
rechunk.py   Zarr v3 -> 重分块/重压缩后的 Zarr v3
~~~

第一版只接受同时包含以下三个维度的输入 Zarr：

~~~text
(time, lat, lon)
~~~

不支持只有 (lat, lon) 的二维 Zarr，也不支持缺少任一标准维度的输入。输入必须为
Zarr v3；遇到 Zarr v2 时应明确报告版本不匹配，而不是静默生成 v2 输出。

重分块只改变数据布局和编码方式，不改变数据值、dtype、坐标、维度长度、变量集合
或属性。第一版只支持无损压缩，不进行量化、舍入或其他有损精度处理。

## 2. 总体流程

~~~mermaid
flowchart TD
    A[运行 rechunk.py] --> B[输入源 Zarr 和输出目录]
    B --> C[打开 Zarr v3 元数据]
    C --> D{是否为 Zarr v3?}
    D -- 否 --> E[报告版本不支持并停止]
    D -- 是 --> F[检查 time/lat/lon 是否全部存在]
    F --> G{三维标准维度是否完整?}
    G -- 否 --> H[报告当前版本只支持完整三维 Zarr]
    G -- 是 --> I[展示数据集和变量信息]
    I --> J[展示当前 chunks 和 codec]
    J --> K[用户选择重分块策略]
    K --> L[根据数据和策略自动计算 chunks]
    L --> M[展示执行计划和 chunk 大小]
    M --> N[探测整数型/浮点型变量]
    N --> O{是否启用重压缩?}
    O -- 否 --> P[保留当前 codec]
    O -- 是 --> Q[用户选择压缩方案]

    W --> U

    U --> Y[多进程/Dask 重分块和重压缩]
    Y --> Z[显示实时进度和吞吐]
    Z --> AA[校验维度、坐标、属性、dtype 和抽样值]
    AA --> AB{校验通过?}
    AB -- 否 --> AC[报告失败且不替换已有目标]

    AD --> AE[报告输出位置和最终 chunks/codec]
~~~

## 3. 输入检查

程序首先只读取元数据，不立即载入全部数据。至少展示：

- Zarr 格式版本；
- time、lat、lon 的长度、dtype 和坐标范围；
- 每个数据变量的维度、shape、dtype 和逻辑数据量；
- 当前 chunk 布局和 codec；
- 变量属性、全局属性和目标磁盘可用空间。

主要数据变量用于计算自动分块方案，坐标变量单独处理，不能因为坐标数组很小而
影响三维数据变量的 chunk 规划。

## 4. 三种分块策略

### 4.1 时间连续型

~~~text
(time, lat, lon) = (完整时间长度, 自动计算, 自动计算)
~~~

整个时间轴位于同一个 chunk 中，适合频繁提取某个空间点的完整时间序列。

### 4.2 空间连续型

~~~text
(time, lat, lon) = (自动计算, 完整纬度长度, 完整经度长度)
~~~

完整空间范围位于同一个 chunk 中，适合频繁提取某一时间点的完整空间场。若完整
空间 chunk 过大，程序必须提前报告内存和单次 I/O 风险。

### 4.3 自定义分块

用户输入三个正整数，例如：

~~~text
[10, 300, 300]
~~~

表示：

~~~text
time chunk = 10
lat  chunk = 300
lon  chunk = 300
~~~

数字是每个 chunk 的长度，不是 chunk 的数量。程序必须检查元素数量、数值类型、
正数约束以及不能超过对应维度长度。

## 5. 自动 chunk 计算

128 MiB 是默认目标值，不是固定结果。程序根据输入数据和策略计算实际 chunks。

~~~text
chunk_bytes = time_chunk * lat_chunk * lon_chunk * dtype.itemsize
~~~

实际计算规则：

1. 读取所有主要数据变量的 dtype，使用最大单元素字节数作为保守基准；
2. 根据可用内存和 worker 数，在 32～256 MiB 范围内调整目标值；
3. 时间连续型固定 time_chunk=ntime，再根据目标值求空间 tile；
4. 空间连续型固定 lat_chunk=nlat、lon_chunk=nlon，再根据目标值求时间长度；
5. 自定义型直接校验用户输入，不自动改写；
6. 将空间块取为接近数据宽高比例的规整尺寸，并裁剪到实际维度范围；
7. 展示实际 chunk 大小、预计 chunk 数和内存占用。

压缩率不用于决定内存安全边界，因为压缩率会随变量和区域变化。它可以通过抽样
写入估算最终磁盘占用，但 chunk 的主要约束仍然是未压缩大小。

对于源 chunk 与目标 chunk 差异很大的数据，不能直接使用无界的一次性 Dask
rechunk。执行器先按源物理 chunk 流式写入与最终空间块对齐的中间 Zarr，再从中间块
沿 time 维度构建最终块；每个源 chunk 只读取一次，局部任务图和并发量均受内存上限
约束。阶段 1 和阶段 2 都把一个逻辑块作为单次批量写入交给 Zarr codec pipeline，
并直接使用 Dask 的物理 chunk，减少重复索引图、小文件调用和 Python 层线程调度。
时间连续策略下，阶段 1 按源 time chunk 隔离并行任务，阶段 2 按最终 chunk 隔离并行
任务；同一块机械硬盘默认限制为两个进程，SSD 或分离设备才允许更高并发，避免并发
进程把顺序 I/O 退化为随机寻道。
启用重压缩时，中间层使用快速 codec，最终层使用用户选择的 codec，避免在临时数据
上重复执行高等级压缩。

阶段 2 会将多个相邻的中间逻辑 chunks 合并为一个受内存上限约束的读取区域，再
批量写出对应的最终 chunks。预计中间逻辑 chunk 数达到约 1,000,000 以上且当前
Zarr 版本支持时，阶段 1 才额外使用 Zarr v3 sharding：逻辑 chunks 仍保持源 time
chunk 和最终空间块对齐，但多个相邻空间逻辑 chunk 会被打包到一个物理 shard 文件
中；time shard 边界不跨越并行任务，避免 worker 之间写同一个 shard。shard 的未
压缩大小控制在约 16 MiB、阶段 2 读取区域控制在约 256 MiB 以内。较小的数据默认
使用普通中间 chunk，避免 sharded 解码开销。阶段 2 的最终输出始终是普通 Zarr v3
chunks，因此不会改变用户看到的最终 chunk 布局。

示例：

~~~text
数据形状：8035 x 768 x 1536
dtype：float32
目标大小：128 MiB

时间连续型：chunks=(8035, 64, 64)
空间连续型：chunks=(28, 768, 1536)
~~~

## 6. 重压缩方案

选择策略后，程序按变量展示 dtype 和当前 codec，并询问是否启用重压缩。重压缩只
重新编码数据，不改变数据值。

| 方案 | 建议配置 | 适用场景 |
|---|---|---|
| 快速读取型 | Zstd 低等级，配合适合 dtype 的 shuffle | CPU 较弱或希望尽快完成 |
| 平衡型（默认） | Zstd level 3～5，整数优先 bitshuffle，浮点优先 shuffle | 综合平衡 |
| 极致压缩型 | Zstd level 9 左右，配合 shuffle/bitshuffle | 更关注输出体积 |

类型处理建议：

- 整数变量优先使用 bitshuffle；
- 浮点变量优先使用 shuffle；
- 布尔变量使用轻量压缩；
- 坐标变量可采用快速方案；
- 字符串或对象变量第一版需要单独检查，不应强行套用数值变量 codec。

实现时使用 Zarr v3 的 codec 配置，不使用只适用于 Zarr v2 的旧式编码字段。
如果用户选择不重压缩，程序应保留当前 codec；当前 codec 不适合 Zarr v3 时应报告错误。

## 7. 输出目录和安全写入

~~~mermaid
flowchart LR
    A[检查输出路径] --> B{路径不存在?}
    B -- 是 --> C[创建临时输出目录]
    B -- 否 --> D{目录为空?}
    D -- 是 --> E[询问是否使用该目录]
    D -- 否 --> F[询问是否覆盖]
    F -- 是 --> G[只允许覆盖已识别的 Zarr]
    F -- 否 --> H[生成 name_rechunked_1、name_rechunked_2 ...]
    E --> C
    G --> C
    H --> C
    C --> I[写入临时目录]
    I --> J{完成且校验通过?}
    J -- 否 --> K[不替换已有目标]
    J -- 是 --> L[原子移动为最终目录]
~~~

用户选择覆盖时，只能删除已经确认是 Zarr store 的目标目录，不能删除普通非空
目录。选择不覆盖时，自动递增目录后缀直到找到可用路径。

## 8. 验证要求

重分块完成后至少验证：

- 输出仍为 Zarr v3；
- time、lat、lon 顺序和长度不变；
- 变量集合、dtype 和属性保持一致；
- chunks 与用户选择或自动计划一致；
- codec 与压缩方案一致；
- 从多个时间点和空间区域抽样读取，数值与输入一致；
- 输出可以被 xarray.open_zarr(..., consolidated=False) 正常打开。

中断或校验失败的临时目录不得被报告为有效结果。

## 9. 预定目录职责

~~~text
convert.py                         # 模块一：源数据转换入口
rechunk.py                         # 模块二：重分块入口（实现阶段创建）
src/fast_nc_zarr/                  # 模块一现有实现
src/fast_nc_zarr/rechunking/       # 模块二的独立实现边界
docs/RECHUNK_WORKFLOW.md           # 本文档
docs/CONVERTER_WORKFLOW.md           # 模块一流程文档
tests/                             # 两个模块的自动化测试
~~~

重分块模块后续建议拆分为输入检查、chunk 规划、codec 规划、执行引擎和结果校验，
避免把第二模块逻辑直接塞入现有转换器的 cli.py。
