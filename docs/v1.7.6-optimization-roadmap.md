# Fast NC Zarr v1.7.6 优化路线图

- **目标版本**：v1.7.6
- **基线版本**：v1.7.5
- **适用范围**：个人用户遥感数据转换、重采样、重分块与桌面端长任务运行
- **路线依据**：v1.7.5 P1 实现、真实 GLASS-PAR 子集 benchmark、现有 Python/Rust parity 约束

## 1. v1.7.5 P1 已交付

### 1.1 filename 模式按 chunk owner 批量写入

`src/fast_nc_zarr/filename_mode.py` 的 filename writer 现在以连续时间批次和空间块作为写入 owner：

1. worker 先打开本批次涉及的源文件；
2. 对一个 `(time_batch, y_block, x_block)` 构造完整的 NumPy buffer；
3. 每个变量对对应的 Zarr 物理 chunk 只执行一次切片写入；
4. 缺失时间仍在同一 buffer 中填充变量的有效 fill value；
5. 轴反转、变量转换和变量重命名保持原有语义。

任务会拒绝不连续或不符合 chunk 边界的时间索引，避免重新引入并发 read-modify-write。返回 metrics 新增：

- `write_mode = "chunk-owner"`
- `chunk_owner_writes`

这项修改消除 filename 模式中逐时间片写入同一压缩 chunk 的主要写放大来源。当前代码没有把未经生产级大样本复测的吞吐提升写入承诺；发布判断应以真实输入 benchmark 为准。

### 1.2 pipeline 长阶段进度事件

`src/fast_nc_zarr/pipeline/engine.py` 新增 best-effort stage heartbeat：

- `conversion`
- `resampling`
- `mathematical_validation`
- `finalization`

每个阶段开始即写入一条 `event = "progress"`，随后默认每 10 秒写入一次。事件携带：

- `stage`
- `heartbeat`
- `sequence`
- `elapsed_seconds`
- `observed_bytes`
- `observed_files`
- `temporary_bytes`
- `throughput_mib_s`
- `stage_checkpoint`
- `terminal_status`

观测值来自临时目录和当前阶段输出路径的文件系统快照，不伪造“已完成任务数”。遥测写入失败不会使有效数据任务失败；heartbeat 线程也不修改 manifest，避免与主执行线程产生写入竞争。

### 1.3 空间 worker benchmark

使用真实 `/run/media/owen/HDD/zarr-convert/GLASS-PAR.zarr` 创建可控 benchmark 输入：

- source subset：`time=64, lat=128, lon=256`
- 输入 chunk：`(16, 16, 32)`
- method：`bilinear`
- target resolution：`0.25°`
- target extent：`lat=[77.3, 89.9]`, `lon=[-179.9, -154.5]`
- `compute_workers=2`
- `time_block=16`
- 16 个空间 chunk owner、64 个时间批次
- `space_workers=2/3/4` 各执行 2 次

实测结果（墙钟时间包含 worker 启动和发布开销）：

| space workers | resolved | 两次墙钟时间（秒） | median（秒） | median 阶段 elapsed（秒） | 吞吐（MiB/s） |
|---:|---:|---:|---:|---:|---:|
| 2 | 2 | 4.563 / 3.848 | 4.205 | 3.665 | 0.340 / 0.353 |
| 3 | 3 | 3.469 / 3.593 | 3.531 | 3.291 | 0.394 / 0.378 |
| 4 | 4 | 3.486 / 3.557 | 3.521 | 3.269 | 0.394 / 0.383 |

所有结果均写出相同的 `1,331,712` logical bytes、`16` 个 tiles 和 `64` 个 time batches；owner buffer 峰值均为 `32,768` bytes。该结果表明在此小型、压缩源、HDD 输出样本上，3 和 4 个空间 worker 基本持平，不能据此把生产默认值直接改成 4。大规模生产任务仍需同时观察 RSS、HDD 吞吐和完整任务墙钟时间。

## 2. v1.7.6 P1：优先完成

### 2.1 native resampling 支持压缩 Zarr 区域读取

当前 native regular resampling 的快速路径要求源数组具备 direct values；压缩 Zarr 和某些 codec 组合会回退到 Python/xESMF。v1.7.6 应实现：

- 读取目标空间窗口对应的 Zarr region；
- 解码实际 v3 codec，而不是把压缩 chunk 当作可直接映射的裸 buffer；
- 对 source chunk、target tile、time block 建立明确的内存上界；
- 在无法安全解码时保留结构化 fallback reason。

验收：压缩 source 与未压缩 source 的 native/Python 数值 parity；输出 metadata、dtype、fill value 和 chunk layout 一致；取消和失败不发布半成品。

### 2.2 Rust native 缺失值语义与 xESMF parity

Rust native bilinear/nearest 当前不能简单假设全部输入 finite。需要显式覆盖：

- `skipna`
- `na_thres`
- 全缺失 source window
- 局部缺失 source window
- 权重归一化
- 边界外点和降级路径
- `fill_value` / NaN 输出语义

验收采用固定 parity fixtures，至少包含 nearest、bilinear、反向纬度、局部 NaN、全 NaN 和边界 tile；误差阈值与现有数学验证规则一致。

### 2.3 压缩源与缺失值回归 fixture

新增可提交的小型 Zarr v3 fixtures，分别覆盖：

- Blosc/Zstd 压缩 source；
- `float32` NaN fill；
- 整型 missing value；
- 多变量共享与不共享空间 chunk；
- source chunk 与 target chunk 不对齐。

fixture 必须可被 Python 与 Rust 路径共同读取，避免只在当前开发机的真实数据上验证。

## 3. v1.7.6 P2：性能与调度

### 3.1 RSS calibration 替代固定 ESMF baseline

当前自动调度使用保守的 `4 GiB` worker baseline。不要直接降低常数。建议流程：

1. 用一个真实 tile 建立 source/window/target 组合的 RSS calibration；
2. 对 `space_workers=2/3/4` 做小样本 A/B；
3. 记录进程峰值 RSS、读取吞吐、写入吞吐、墙钟时间和失败率；
4. 根据目标机器和存储介质选择 worker 数，而不是按 CPU 利用率单指标选择。

校准结果必须有安全余量，并在内存不足时 fail-safe 降级。

### 3.2 统一进度模型

v1.7.5 已提供 pipeline 文件事件，但 `observed_bytes` 仍是存储观测值，不等价于业务完成度。v1.7.6 应在 conversion、resampling、rechunking 内部暴露：

- `completed`
- `total`
- `logical_bytes`
- `temporary_bytes`
- `throughput_mib_s`
- `rss_bytes`
- `eta_seconds`（仅在样本足够时提供）

IPC 层继续使用 `progress` 事件，区分：

- 请求 backend；
- resolved backend；
- capability fallback；
- storage observation；
- logical task completion。

### 3.3 filename writer 生产级 A/B

以完整 filename 数据集验证 v1.7.5 chunk-owner writer，至少对比：

- partial-chunk 旧写法基线；
- chunk-owner 新写法；
- 不同 `chunk_time`、`chunk_lat`、`chunk_lon`；
- 1/2/4 worker；
- 压缩与无压缩输出；
- 有缺口和无缺口时间轴。

记录 logical throughput、physical bytes、write amplification、source opens、RSS 和最终数组 parity。没有完整结果前，不把某个 chunk 参数硬编码为全局默认值。

## 4. v1.7.6 P3：架构级优化

### 4.1 filename/HDF native hyperslab reader

在证明 codec 解码和缺失语义 parity 后，再评估 HDF/filename 模式的 native hyperslab reader。目标是减少 Python coordinator、重复 dataset open 和跨语言复制，但必须先解决：

- HDF group/dataset 映射；
- scale/offset 与 missing value；
- CRS 与 GeoTIFF scalar coordinate；
- 不同文件网格一致性校验；
- 取消、错误清理和 Windows/Linux 路径差异。

### 4.2 conversion 与 resampling 融合

直接从 raw HDF block 进入 resampling 可以消除 source-crop 中间 Zarr，但可能导致同一 raw 文件被多个空间 tile 重复读取。只有在 source read amplification、随机 I/O 和文件打开成本有实测证据后再实施；默认先保留 staging checkpoint 的可恢复性。

## 5. 发布验收门槛

v1.7.6 至少需要：

1. `pixi run version-check`、`pixi run contract-check` 通过；
2. Python 全量测试、Rust workspace 测试通过；
3. native 与 Python parity fixtures 通过；
4. 压缩 source、NaN、整型 fill 和轴反转场景通过；
5. 真实数据 benchmark 报告 worker 数、RSS、HDD 吞吐、墙钟和写放大；
6. 桌面端看到 progress 事件时，不把 storage observation 显示为虚假的百分比；
7. 失败、取消、磁盘不足和 stale staging 均不发布不完整 Zarr。

## 6. 当前决策

- **已选择**：v1.7.5 先采用 filename chunk-owner 批量写入和 best-effort pipeline heartbeat，改动局部、可回滚、保持现有数据语义。
- **暂不选择**：直接降低 ESMF 固定内存 baseline、立即融合 raw conversion/resampling、宣称 native 已覆盖压缩 NaN source。
- **下一步默认顺序**：压缩 Zarr native 读取 → missing-aware Rust parity → 小样本 RSS calibration → 完整生产 benchmark → 再评估 native hyperslab 和阶段融合。
