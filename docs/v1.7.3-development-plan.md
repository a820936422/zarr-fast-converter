# v1.7.3 开发方案

> 状态：开发中
> 维护分支：`develop`
> 基线提交：`73fceb1`（v1.7.2 native-first desktop entry）
> 方案日期：2026-08-13

## 1. 版本目标

v1.7.3 的主题是 **Rust native parity 与桌面运行时生产化**。本版本不再优先扩展 UI，而是让已有 Tauri 工作台具备可恢复、可诊断、可验证的运行时，并逐步扩大 Rust native 的真实覆盖范围。

目标架构：

```text
React + TypeScript
        ↓ typed Tauri commands
Rust desktop coordinator
        ├── 已通过正确性门的 native stages
        ├── task registry / events / manifest / recovery
        └── capability 不足时使用兼容处理服务
```

核心原则：

- 未通过正确性门的操作不得伪装成 native 成功；
- 每个阶段记录 requested backend、resolved backend 和 fallback reason；
- 任务先写入 staging，验证通过后原子发布；
- Rust coordinator 逐步成为 pipeline 的 canonical coordinator，但不在本版本强行删除兼容路径；
- 先保证结果语义和恢复安全，再追求性能；
- 先完成可观测证据，再收缩 Python 兼容实现。

## 2. 当前基线和缺口

当前 `develop` 已包含 v1.7.0 至 v1.7.2 的线性历史，已有能力包括：

- Tauri + React + TypeScript 桌面工作台；
- Rust task event、取消、资源快照和 capability matrix；
- Zarr v3 结构检查；
- Float32/Float64 chunk、region 和数组写入；
- 单变量 Float32/Float64 重分块；
- staging 校验和原子发布；
- Python 兼容服务作为未完成 native parity 的安全边界。

当前 capability matrix 明确未完成：

```text
zarr.rechunk_multi
raw.netcdf.inspect
raw.netcdf.convert
resample.nearest
resample.bilinear
pipeline.native
```

当前运行时还存在以下 v1.7.3 重点问题：

1. task registry 只存在于进程内，应用重启后任务历史丢失；
2. 任务状态、manifest 和 checkpoint 尚未形成完整的重启恢复闭环；
3. Tauri command 依赖的 `AppState` 和 `TaskRegistry` 必须在应用启动时显式注册；
4. 多变量、整数 dtype、fill/scale、CF 属性和复杂 codec 尚未达到 Rust parity 门槛；
5. 标准 NetCDF native reader 尚未实现；
6. native nearest/bilinear 尚未实现；
7. 跨平台桌面启动和发布包验证仍需持续加强。

## 3. 里程碑顺序

### P0：桌面运行时稳定性和任务持久化

**目标**：应用重启后仍能看到任务历史，并能从保留的 pipeline checkpoint 进入恢复流程。

开发内容：

- 显式注册 `AppState` 和 `TaskRegistry`；
- 将 task summary 持久化为用户状态目录下的 JSON；
- 使用 schema version 和临时文件原子替换；
- 启动时加载历史任务；
- 将上次退出时仍为 running/cancelling 的任务标记为可诊断的 interrupted/failed 状态，不伪造为成功；
- 清理失效 cancellation handle；
- 前端启动时加载持久化任务，任务中心保留 checkpoint recovery 入口；
- 为持久化、损坏文件、重启中断和终态更新增加 Rust 行为测试。

任务状态文件策略：

- `FAST_NC_ZARR_TASK_STATE` 可用于测试和受控部署时指定文件；
- Linux 默认使用 `$XDG_STATE_HOME/fast-nc-zarr/tasks.json`，没有该变量时使用 `$HOME/.local/state/fast-nc-zarr/tasks.json`；
- macOS 使用 `~/Library/Application Support/fast-nc-zarr/tasks.json`；
- Windows 使用 `%LOCALAPPDATA%\\fast-nc-zarr\\tasks.json`；
- 状态文件只保存 task summary，不保存输入数据或大对象；
- 具体科学结果仍以 pipeline manifest、events 和 checkpoint 为准。

P0 验收：

- 新任务插入、资源更新、失败、取消和完成均能落盘；
- 新建 registry 能读取上一实例的终态任务；
- 上一实例退出时的 running/cancelling 任务不会显示为 running；
- 损坏或旧 schema 状态文件不会阻止桌面应用启动；
- `list_tasks` 在 Tauri 启动后可用；
- 前端任务中心能显示持久化历史，并可继续使用 checkpoint recovery；
- Rust 单元测试和 desktop TypeScript 检查通过。

### P1：Rust Zarr parity

**目标**：完成可验证的多变量 Zarr native 发布路径。

范围：

- 多变量原子发布；
- 整数 dtype；
- coordinate/data-variable 区分；
- fill value、scale/offset 和 CF 属性保持；
- 多变量 codec 选择与验证；
- 多变量取消、失败清理和 checkpoint；
- Python/Rust golden fixture 对照。

验收：

- 变量集合、dims、shape、dtype、chunks、attrs 和 codec 一致；
- 取消和异常不会发布半成品；
- overwrite 和已存在输出目录行为一致；
- capability 只在正确性测试通过后改为 supported。

### P2：标准 NetCDF native reader

**目标**：先实现一个边界清晰、可跨平台验证的 NetCDF 子集，而不是一次性重写所有 HDF-EOS/TIFF/非标准数据。

第一批范围：

- NetCDF-4/classic 常见结构；
- 标准 `time`、`lat`、`lon`；
- 数值型三维变量；
- 标准 CF time；
- 基本属性和缺测值；
- 单文件和批量文件检查。

顺序：

1. `raw.netcdf.inspect`；
2. Python reference 对照；
3. `raw.netcdf.convert`；
4. 真实数据、异常、取消和发布验证。

复杂 HDF、HDF-EOS、TIFF、非标准 calendar 在本阶段继续使用兼容路径，并在 capability 中明确说明。

### P3：基础 native resampling

**目标**：实现规则经纬度网格上的基础 nearest/bilinear，保持明确的边界语义。

第一批范围：

- nearest；
- bilinear；
- Float32/Float64；
- lat 正序和倒序；
- 基本缺测值；
- 分块处理和有界并行；
- 取消、staging 和原子发布。

暂不纳入：

- conservative、patch 等复杂方法；
- 非规则网格；
- 复杂 xESMF 边界语义；
- 未定义的缺测值统计策略。

重点测试中心区域、边界像元、坐标方向、跨 chunk 边界和 NaN 传播。

### P4：Pipeline native stage integration

**目标**：让 Rust 成为 pipeline coordinator，并按 capability 将每个阶段路由到 native 或兼容路径。

阶段事件必须包含：

- requested backend；
- resolved backend；
- fallback；
- fallback reason；
- stage checkpoint；
- manifest 路径；
- terminal status。

不要求 v1.7.3 末尾删除 Python worker。要求先把 native 和兼容阶段放入同一套 manifest、events、recovery 语义中。

### P5：跨平台发布和兼容路径收缩

**目标**：验证 Linux X11/Wayland、Windows、macOS 的桌面启动、sidecar 和发布包行为。

范围：

- Linux X11/Wayland 启动 smoke；
- Windows/macOS 构建配置检查；
- sidecar 缺失、启动失败和权限错误；
- 发布包内资源、字体和 worker 路径；
- 只有在 native parity、真实数据 A/B 和恢复门全部通过后，才删除对应 Python 兼容代码。

## 4. 明确不做的事情

本版本不做：

- 一次性重写所有 NetCDF/HDF/TIFF/xESMF 能力；
- 在没有 golden fixture 的情况下扩大 capability；
- 在 native parity 完成前删除 Python fallback；
- 为了“看起来 native”而改变科学结果语义；
- 在后端运行时未稳定前继续扩张 UI 功能；
- 引入没有明确跨平台收益的大型新依赖。

## 5. 验证门

每个阶段必须至少通过对应验证：

```bash
pixi run desktop-typecheck
pixi run desktop-build
pixi run rust-test
pixi run test
```

涉及桌面启动时还必须运行实际入口：

```bash
pixi run gui
```

数据能力变更必须同时具备：

- 单元测试；
- deterministic fixture；
- 真实数据 smoke 或 A/B；
- manifest、events 和 capability 证据；
- 取消、异常和恢复路径验证。

## 7. 变更准入标准

修改 capability、manifest schema 或 IPC payload 前，必须先更新对应 contract、fixture、Rust/TypeScript 类型和行为测试。任何 fallback 都必须显式记录原因；任何删除兼容路径的提交都必须同时删除已失效的配置、文档和测试，不保留无效别名。
