# Fast NC Zarr v1.7.7 优化路线图

- **目标版本**：v1.7.7
- **基线版本**：v1.7.6
- **文档更新**：2026-08-17
- **适用范围**：个人用户遥感数据转换、Zarr v3 重采样、重分块、压缩和桌面端长任务

本文档承接 v1.7.6 的发布闭环。v1.7.6 已把正确性、原子发布、native capability fallback、任务生命周期和长阶段可观测性作为基础约束；v1.7.7 只推进有实测证据支撑的性能与格式覆盖，不把实验性 native 路径伪装成默认成功路径。

## 1. v1.7.6 已固化的基线

### 1.1 数据与发布不变量

- 最终输出固定为 Zarr v3，规范维度为 `time`、`lat`、`lon`。
- 转换、重采样和重分块均先写 UUID 隔离的 staging；结构、codec、样本和语义校验通过后才发布。
- 取消、异常、源文件变化、磁盘不足和 backend capability 不满足时不得发布部分结果。
- native 路径只在 capability matrix 证明的 dtype、fill、codec、layout 组合上执行；其他组合必须保留结构化 fallback reason。

### 1.2 已完成能力

- filename 模式采用 chunk-owner 批量写入，避免同一压缩 chunk 的逐时间片 read-modify-write 放大。
- pipeline 预算拆分为 conversion/resampling、rechunk、compression candidate 三类独立预算，并贯通 UI、IPC、manifest、事件和 recovery。
- Rust native resampling 覆盖已验证的压缩 Zarr v3 region 解码、缺失值语义和 float32 parity fixture；未覆盖 codec 仍回退 Python。
- worker 生命周期、取消、异常清理和 Linux parent-death cleanup 已形成 manifest 与回归测试闭环。
- 按变量 resampling override、任务历史清理和桌面端任务 registry 已贯通前后端。
- pipeline 阶段事件已区分逻辑完成度和 filesystem observation：conversion、resampling、rechunk finalization 都可报告统一的 `completed`、`total`、`logical_bytes`、`temporary_bytes`、`rss_bytes` 和 ETA 字段；resampling/rechunking 的分块或阶段回调不再把文件字节数误当业务完成度。
- 2026-08-17 的真实全量运行暴露出一个未闭环的边界：filename conversion 事件的 `total=17,487,360,000`，而最终 conversion metrics 的 `logical_bytes=34,974,720,000`；事件在 `32/64` 个时间任务时先达到 100%，随后仍继续运行到 `64/64`。v1.7.7 已加入 effective output dtype/layout 统一计算和 task/byte 对账代码；在真实 GLASS 全量任务再次确认前，该项仍不标记为完全关闭。

### 1.5 2026-08-17 全量运行基线与新结论

本次真实任务从 `/run/media/owen/HDD/zarr-convert/raw` 生成 `GLASS-EVI.zarr`，最终 `status=succeeded`，总耗时 `577.44 s`。本次结果可以作为 chunk-owner 和 pipeline 阶段观测基线，但不是旧实现 A/B 结果。

- 计划：filename conversion `workers=4`、`chunk_time=16`、`chunk_lat=514`、`chunk_lon=513`、`64` 个时间任务；resampling 使用 `conservative`、`float32`、`tile_size=1024`、`time_block=16`、`compute_workers=2`、`space_workers=3`。
- conversion：`186.52 s`，最终有效逻辑写入 `34,974,720,000` bytes，`178.83 MiB/s`，峰值 RSS `4.89 GiB`，`64` tasks，`2,880` chunk-owner writes。
- resampling：`311.85 s`，逻辑输出 `8,743,680,000` bytes，物理输出 `3,199,317,863` bytes，`26.74 MiB/s`，`90` tiles、`5,760` time batches；三个空间 worker 的 aggregate tile elapsed 不能直接当墙钟耗时。
- requested `rechunking` 和 `recompression` 在当前 output layout 下被融合，physical stages 只有 `conversion`、`resampling`，`finalization=not_required_direct_layout`；manifest 必须让 UI 明确显示“请求的操作已由前置阶段满足”，而不是显示为遗漏。
- source 和 output 位于同一 rotational HDD，temporary 位于 SSD；本次 resource budget 为约 `26.88 GiB`，worker ceiling 为 `6`。该存储拓扑会同时放大 source read 与 final publish 的 HDD 争用，后续 A/B 必须记录并区分存储拓扑。
- 本次配置 `cleanup_intermediate=false`；任务成功发布 `3.20 GB` 最终输出后仍保留约 `8.66 GB` 的 `source-crop.zarr` checkpoint。该行为不是发布失败，但必须在 UI、磁盘预检和任务清理策略中明确告知用户，并纳入成功后磁盘保留/清理验收。
- worker lifecycle 最终为 `completed`；resampling 的 3 个空间 worker 已退出，桌面 worker 也已回收，没有观察到残留任务进程。

本次运行还验证了 resampling 的 tile progress 单调增长、ETA 随有效逻辑吞吐收敛；同时验证 `temporary_bytes` 在 resampling 中会因 chunk 覆写而上下波动，因此它只能作为存储观测量，不能作为完成百分比。

### 1.6 2026-08-17 FLUXSAT 全量结构检查基线

本轮候选全量数据改为 `/run/media/owen/EXTERNAL_USB/数据集/FLUXSATv2/NC_v2.2/`。该批次包含 `264` 个按月 NetCDF 文件、`8,035` 个连续日时间点，覆盖 `2001-01-01` 至 `2022-12-31`，由 complete 模式和 `h5netcdf` 读取。

- 初次完整结构检查只报告 `200108` 和 `202202` 两个文件“变量定义与首文件不同”；经逐字段对比，差异全部来自 CF 辅助变量 `time_bnds`：`200108` 增加了 `units=days since 2000-01-01`，`202202` 将 dtype 从 `float64` 改为 `int64`。
- 三个文件的 `time_bnds` 仍一致表达每日中心时间的 `[-0.5, +0.5]` 边界；经纬度网格以及 `GPP`、`GPP_uncertainty`、`FPAR_LUE_constitutive`、`BRDF_Quality`、`Percent_Inputs` 五个可处理数据变量的名称、维度、dtype、shape 和关键属性没有差异。因此原错误是把不写入标准产品的 bounds/CRS 元数据当成数据变量进行严格批次对比造成的误拒绝，不是科学数据结构损坏。
- 结构检查现已排除由 CF `bounds`、`climatology`、`geometry`、`grid_mapping` 和坐标属性引用的辅助变量，同时继续严格核对实际数据变量和经纬度网格。真实 `264` 文件完整扫描已通过，识别为 complete 模式、五个可处理变量、无时间缺口。
- 修正结构误拒绝后，完整检查快照直接放入 JSONL 事件会产生 `1,092,909` bytes 的单行消息，超过 Tauri worker 的 `1,048,576` bytes 上限。桌面 IPC 现只发送 UI 所需的紧凑摘要，完整逐文件 inventory 和坐标数组保留在磁盘快照；同一真实检查的最大事件降至 `6,180` bytes，terminal event 为 `finished`。
- 该证据只覆盖 complete 模式的真实结构检查，尚不代表全量转换、重采样或发布成功，也不能替代 GLASS 或等价 filename 模式真实数据对 chunk-owner progress 的复测。

## 2. v1.7.7 优先级

### P0：故障注入与发布可靠性矩阵
**状态：第一批代码与回归已完成；已覆盖真实子进程崩溃模拟，P0 矩阵仍待真实 ENOSPC、跨存储环境和长任务故障注入后关闭。**

已完成的第一批边界：

- raw 与现有 Zarr pipeline 的取消异常现在写入 `status=cancelled`、`terminal_status=cancelled` 和 `worker_lifecycle.exit_reason=cancelled`，不再把取消伪装成失败；
- 成功任务分别覆盖 `cleanup_intermediate=true/false` 的 checkpoint 删除与保留；失败任务保留已验证 conversion checkpoint；
- recovery 拒绝越出任务目录的 checkpoint 路径；publication 拒绝跨文件系统 staging；已有 executor failure、capacity preflight、overwrite、symlink 和恢复测试继续通过；
- `bounded_process_map` 新增真实子进程 `os._exit` 崩溃测试，确认 BrokenProcessPool 路径进入统一 worker 清理；
- 完整 Python 回归当前为 `219 passed`、`33 subtests passed`、1 个既有 Zarr warning。


### P0.1：逻辑 progress、effective dtype 与 terminal metrics 对账
**状态：代码修正已完成；dtype widening fixture、targeted tests 和完整 Python 回归已通过；真实 filename 模式（GLASS 或等价数据）全量复测待执行。FLUXSAT complete 模式只提供补充门禁，不能替代 filename 路径。**

已完成的代码边界：

- `selected_output_logical_bytes(...)` 统一按 effective output dtype 计算 conversion logical total；显式 `OutputLayout` 优先，缺省变量回退到 transform dtype；
- complete、filename、Dask conversion、preview、自动调优磁盘估算和 direct writer 使用同一份逻辑字节契约；
- `scale_factor`/`add_offset` 导致整数输出 widening 时，进度分母与 worker 实际输出字节保持一致；
- filename gap conversion 和 complete conversion 均增加了终值对账测试。

当前验证证据：targeted conversion/filename/service tests `25 passed`；新增 CF 辅助元数据结构 tests `2 passed`；完整 Python 回归 `219 passed`、`33 subtests passed`、1 个既有 Zarr warning；相关 Python 文件 `py_compile` 通过。

本次全量运行证明“字段存在”不等于“完成度语义正确”。新增验收要求：

- conversion/resampling 每个阶段的 `total` 必须与 terminal metrics 的 `logical_bytes` 对齐；输入 dtype、scale/offset、fill 转换导致输出 dtype 变化时，分母必须使用最终有效输出 dtype；
- `completed` 不得在任务计数尚未结束时达到 `total`；必须同时对账 task count、worker 累计 bytes、stage terminal event 和 manifest metrics；
- 事件序列必须单调，terminal `completed=total` 只能出现在阶段真正完成时；
- UI 在 stage 仍为 `running` 且后续任务尚未结束时不得显示 100%；
- 增加一个真实的 int16/float16 → float32 filename conversion fixture，覆盖“进度提前 100%”边界；
- 记录 `temporary_bytes`、`observed_bytes` 的波动，但不把它们用于业务完成度或 ETA 分母。


建立可重复的故障注入测试，不依赖真实大盘数据：

1. conversion/resampling/rechunking 在任务中途取消；
2. worker 崩溃、executor 异常和父进程终止；
3. staging 目录存在、stale manifest、损坏 checkpoint 和恢复；
4. 输出盘空间不足、临时盘空间不足和跨文件系统发布失败；
5. overwrite 对普通目录、符号链接目标、未知格式目录的保护；
6. 每种失败均检查无部分发布、worker 已回收、registry 状态、manifest terminal event 和可排查的 staging 保留策略。
7. 成功且 `cleanup_intermediate=false` 时检查 checkpoint 的保留大小、用户可见提示和显式清理动作；成功且启用清理时检查 checkpoint 确实删除且最终输出不受影响。

验收输出：故障矩阵、每种场景的最终状态、残留进程计数、残留目录类型和恢复结论。

### P0.2：真实 NetCDF 批次结构与 CF 辅助元数据归一化
**状态：误拒绝原因、结构归一化、IPC 负载修正和回归测试已完成；FLUXSAT `264` 文件桌面 JSONL 完整结构检查已通过，全量处理仍待执行。**

- `bounds`、CRS、geometry 和额外坐标等 CF 辅助变量不属于标准 `time/lat/lon` 数据输出，允许其 dtype、units 和编码在批次内存在不影响科学值的差异。
- 实际可处理数据变量仍必须严格匹配名称、维度、dtype、非时间 shape、fill/scale/offset/units；经纬度坐标继续逐文件哈希对比，不能借辅助变量归一化放宽科学数据一致性。
- 回归必须同时证明“辅助 `time_bnds` units/dtype 差异可接受”和“真实数据变量 units/dtype 差异仍被拒绝”，并覆盖直接 HDF5 metadata reader 与 xarray fallback。
- 桌面检查事件必须保持在 `1 MiB` 协议上限内；IPC 摘要不携带逐文件 inventory 和完整坐标数组，但磁盘检查快照必须保留完整恢复信息，后续 preview/run 继续通过快照路径复用检查结果。
- FLUXSAT 全量处理完成后，记录 complete conversion 的 logical total、task count、terminal metrics、变量清单、样本 parity、backend、峰值 RSS、临时空间和发布结果。

### P1：Zarr v3 codec 与科学语义覆盖

继续扩大 native region reader 的 capability matrix，优先覆盖真实用户会遇到且可以建立 parity fixture 的组合：

- Zstd、Blosc-Zstd、Blosc-LZ4、Gzip 之外的 v3 codec；
- `float32`、`float64`、整型 missing value 与 NaN fill；
- CF `scale_factor`、`add_offset`、非有限值和 packed data；
- 日历、时间解码和坐标方向边界；
- 多变量共享/不共享 chunks、源/目标 chunk 不对齐、边界 tile。

每个新增组合必须同时检查 Python/native 数值 parity、dtype、fill value、metadata、chunk layout、取消和 fallback reason。不能只检查数组数值。

### P1：filename writer 完整数据 A/B

用同一份完整真实数据对比旧实现基线和 chunk-owner 实现，至少覆盖：

- `chunk_time`、`chunk_lat`、`chunk_lon` 的小/中/大组合；
- 1/2/4 worker；
- 无压缩、快速压缩和代表性压缩；
- 有缺口和无缺口时间轴；
- source opens、logical throughput、physical bytes、write amplification、峰值 RSS、最终数组 parity。

在完整 A/B 结束前，不修改生产默认 chunks、worker 或内存 baseline。benchmark 输出必须保存候选计划、硬件/存储配置和失败原因。

本次 `GLASS-EVI` 全量运行只能作为新 chunk-owner 基线：它没有同一数据集上的旧 writer 对照，且 source/output 共用 HDD、temporary 使用 SSD；不能据此宣称 chunk-owner 的相对收益或修改默认并发参数。

### P2：native hyperslab reader

只有 codec、缺失值、scale/offset、时间和 CRS 语义 fixture 足够后，才推进统一 HDF/NetCDF/TIFF typed reader。进入条件：

- 定义 dtype、shape、fill、source attributes、内存预算和结构化 fallback reason 的 ABI；
- 明确 HDF group/dataset 映射、GeoTIFF window/CRS/旋转、多 band 和 packed data 语义；
- 对比 Python 读取窗口的 I/O 放大、文件打开次数、峰值 RSS 和取消清理；
- 不改变既有 filename 模式和 NetCDF 维度语义。

### P2：conversion/resampling 融合评估

暂不删除 source-crop checkpoint。只有 staging 路径与 fused 路径在相同 source/target 上完成 A/B，且同时记录 raw read bytes、重复读取比例、source opens、墙钟、峰值 RSS、失败率、恢复性和取消清理后，才决定是否融合。

若融合无法保持可恢复 checkpoint、原子发布或可证明的读取放大上界，保留当前分阶段实现。

### P2：长任务 UI 与诊断细化

- UI 明确区分业务完成百分比、logical bytes、filesystem observation 和 ETA；
- 显示 requested backend、resolved backend、fallback reason 和当前 checkpoint；
- 对长期无逻辑进度但仍有 heartbeat 的阶段显示“处理中”，不显示虚假的 100%；
- 任务详情支持导出 manifest、事件和 worker lifecycle 摘要，便于个人用户提交可复现问题。
- 对输入/输出 dtype 变化、提前达到 100%、checkpoint 保留大小和“请求操作已融合到前置阶段”提供可见诊断。

## 3. 明确不做的事项

- 不因为小样本 benchmark 直接提升默认 worker 数。
- 不把 storage observation 当作业务完成百分比或 ETA。
- 不在 capability、parity 和内存上界不完整时强制 Rust native。
- 不为消除一个 staging 目录而牺牲恢复 checkpoint、原子发布或取消清理。
- 不在没有完整真实数据 A/B 的情况下删除旧实现基线或修改默认 chunks。

## 4. 交付顺序

1. 先完成 FLUXSAT complete 模式全量运行，验证新增结构归一化、logical total、task count、terminal metrics 和样本语义；再用真实 filename 模式（GLASS 或等价数据）复测 chunk-owner progress。两条路径不能互相替代，均通过后才关闭 P0.1/P0.2；
2. 完成 P0 故障注入和 checkpoint 保留/清理矩阵并固化发布证据；
3. 再扩大 codec、missing value、packed data 和时间语义 parity；
4. 同步完成 filename 完整数据 A/B，但保持默认参数不变；
5. 依据证据决定 native hyperslab reader 和 conversion/resampling 融合是否进入实现；
6. 最后补齐 UI 诊断细节，并重新执行全部 Python、Rust、桌面和发布包门禁。

任何未满足验收条件的条目只记录为实验或评估，不写入 v1.7.7 的稳定能力承诺。
