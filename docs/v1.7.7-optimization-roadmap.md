# Fast NC Zarr v1.7.7 优化路线图

- **目标版本**：v1.7.7
- **基线版本**：v1.7.6
- **文档更新**：2026-08-17
- **适用范围**：NetCDF/HDF/TIFF 到 Zarr v3、空间重采样、重分块、压缩和桌面长任务

本文档只保留最近一次真实 GLASS 全量运行结果，以及基于该结果确认的 v1.7.7 待处理事项。旧运行记录、旧性能数字和已停止安排的 FLUXSAT 全量测试不再作为路线图内容。

## 1. 已固化的工程约束

### 1.1 数据与发布不变量

- 最终输出固定为 Zarr v3，标准维度为 `time`、`lat`、`lon`。
- 转换、重采样和重分块先写任务专属 staging；结构、codec、样本和语义校验通过后才原子发布。
- 取消、异常、源文件变化、磁盘不足、backend capability 不满足时，不得发布部分结果。
- 普通非空目录、符号链接目标和未知格式目录不得被 `--overwrite` 删除。
- 恢复只能使用任务目录内、经过 manifest 和结构校验的 checkpoint。
- `cleanup_intermediate=false` 时必须明确保留 checkpoint 的位置和大小；保留 checkpoint 不得被误报为失败。

### 1.2 Backend 与协议约束

- `backend=auto` 必须记录 requested backend、resolved backend、fallback 和 fallback reason。
- 未通过 capability matrix 的 native 操作必须回退 Python，不能伪装成 Rust 成功。
- Python worker 使用 JSONL stdin/stdout；stdout 只承载结构化事件，诊断进入 log event 或 stderr。
- 每个 task 只有一个 terminal event：`finished`、`failed` 或 `cancelled`。
- 阶段运行时的 `completed` 必须小于 `total`；只有 terminal `status=completed` 才能报告 100%。
- `logical_bytes` 用于业务完成度和 ETA；`temporary_bytes`、`observed_bytes` 只表示文件系统观测，不得作为完成度分母。

### 2.5 运行后已修复的边界

本次全量运行暴露两项问题，当前代码已修复并加入回归测试：

1. raw pipeline 在 `backend=auto` 且没有独立 finalization 时，manifest 曾错误记录 Python coordinator 为 `fallback=false`。现在 manifest 和 conversion metrics 会统一记录真实 fallback reason。
2. 阶段最后一次 worker callback 达到逻辑 total 时，历史事件中出现过 `status=running, completed=total`。现在 running progress 被限制为小于 total，只有 terminal completed event 才能显示 100%。

下一次真实 GLASS 或等价任务仍需现场确认这两项修复在完整桌面流程中生效。

## 3. v1.7.7 待处理内容

### P0：故障注入与发布可靠性矩阵

**目标：关闭长任务失败、取消、恢复和发布安全边界。**

待处理：

1. conversion、resampling、rechunking 中途取消。
2. worker 崩溃、executor 异常、父进程终止。
3. stale manifest、损坏 checkpoint、任务恢复和重复恢复。
4. 输出盘 ENOSPC、临时盘 ENOSPC。
5. staging 与 output 跨文件系统时的发布失败。
6. overwrite 对普通目录、符号链接和未知格式目录的保护。
7. 成功任务 `cleanup_intermediate=true/false` 的 checkpoint 删除、保留大小和最终输出完整性。
8. 每种失败均检查：
   - 无部分发布；
   - worker 已回收；
   - registry 状态正确；
   - manifest terminal status 正确；
   - events terminal event 唯一；
   - staging 保留策略可排查。

### P0.1：Progress、dtype 与 terminal metrics 对账

**当前状态：代码和回归已完成；最新 GLASS 运行已证明 logical total 与 terminal metrics 对齐。**

仍需完成：

- 用下一次真实任务确认 running progress 不再提前达到 100%。
- 检查 task count、worker 累计 bytes、stage terminal event 和 manifest metrics 四者一致。
- 增加真实 int16/float16 → float32 filename conversion 运行证据。
- 检查 scale/offset、fill value 和 dtype widening 时 progress denominator 仍使用 effective output dtype。
- 在 UI 中明确区分业务完成度、logical bytes、filesystem observation 和 ETA。

### P0.2：真实源数据结构与 CF 辅助元数据

**当前策略：不再安排 FLUXSAT 全量测试。**

待处理内容改为可重复、代表性和不依赖 FLUXSAT 全量数据的验证：

- CF `bounds`、`climatology`、`geometry`、`grid_mapping` 和额外坐标辅助变量归一化。
- 实际处理变量继续严格校验名称、维度、dtype、shape、fill、scale、offset 和 units。
- 直接 HDF5 metadata reader 与 xarray fallback 保持一致。
- 使用小型代表性 fixture 验证辅助变量差异可接受、科学变量差异必须拒绝。
- 检查 inspection snapshot、紧凑 IPC 摘要和后续 preview/run 的快照复用。

### P1：Zarr v3 native parity

继续扩大 capability matrix，但每个新增组合必须同时验证：

- Python/native 数值 parity；
- dtype、fill value 和 NaN 语义；
- CF `scale_factor`、`add_offset` 和 packed data；
- codec、chunk layout 和 metadata；
- latitude/lon 方向、边界 tile 和时间语义；
- 取消、恢复和 fallback reason；
- 单变量、多变量、共享 chunks 和非对齐 chunks。

优先顺序：

1. 已支持 codec 的更多 missing/fill/packed 组合；
2. 多变量 native region 读取；
3. 时间和 calendar 边界；
4. HDF/NetCDF/TIFF 代表性输入的 parity fixture。

### P1：Filename writer 完整数据 A/B

使用同一份 GLASS 数据对比旧 writer 与 chunk-owner writer。至少记录：

- `chunk_time`、`chunk_lat`、`chunk_lon`；
- 1、2、4 worker；
- 无压缩、快速压缩和代表性压缩；
- 有缺口和无缺口时间轴；
- source opens；
- logical throughput；
- physical bytes；
- write amplification；
- 峰值 RSS；
- 最终数组 parity；
- 失败、取消和 checkpoint 清理行为。

在完整 A/B 完成前，不修改生产默认 chunks、worker 和内存 baseline。

### P1：Conservative resampling 性能 A/B

最近一次 GLASS 运行显示 resampling 中权重构建、读取和重采样占主要成本。下一轮只做可重复测量，不直接修改默认参数：

- conservative 权重构建复用与不复用；
- tile geometry 与 owner chunk 对齐；
- source/output 同 HDD 与分离存储拓扑；
- temporary SSD 与其他临时介质；
- 1、2、3 个 space worker；
- raw read bytes、权重构建耗时、重采样耗时、写入耗时；
- 峰值 RSS、owner memmap、失败率、取消清理和最终 parity。

所有 aggregate tile timing 必须与 wall-clock timing 分开记录。

### P2：Native hyperslab reader

只有 codec、缺失值、packed data、时间和 CRS 语义 fixture 完整后，才推进统一 HDF/NetCDF/TIFF typed reader。

进入条件：

- 定义 dtype、shape、fill、source attributes、内存预算和 fallback reason ABI；
- 明确 HDF group/dataset 映射；
- 明确 GeoTIFF window、CRS、旋转和多 band 语义；
- 对比 Python window 读取的 I/O 放大、文件打开次数、峰值 RSS 和取消清理；
- 不改变既有 filename 模式和 NetCDF 维度语义。

### P2：Conversion/resampling 融合评估

暂不删除 `source-crop.zarr` checkpoint。

只有在相同 source/target 上完成 staging 路径与 fused 路径 A/B，并同时记录以下指标后，才决定是否融合：

- raw read bytes；
- 重复读取比例；
- source opens；
- wall-clock；
- 峰值 RSS；
- write amplification；
- 失败率；
- 恢复性；
- 取消与 checkpoint 清理。

如果融合无法保持可恢复 checkpoint、原子发布或可证明的读取放大上界，保留现有分阶段实现。

### P2：桌面长任务 UI 与诊断

- 显示 requested backend、resolved backend、fallback reason；
- 显示当前 checkpoint 和 checkpoint 保留大小；
- 显示 logical bytes、业务百分比、filesystem observation 和 ETA；
- 运行阶段有 heartbeat 但逻辑进度不变时显示“处理中”，不显示虚假 100%；
- 明确显示“请求的操作已由前置阶段满足”；
- 支持导出 manifest、events 和 worker lifecycle 摘要；
- 对 dtype 变化、fallback、checkpoint 保留和取消清理提供可见诊断。

## 4. 明确不做

- 不再安排 FLUXSAT 数据全量测试。
- 不因为一次真实运行或小样本 benchmark 直接提升默认 worker 数。
- 不把 storage observation 当作业务完成百分比或 ETA 分母。
- 不在 capability、parity 和内存上界不完整时强制 Rust native。
- 不为减少一个 staging 目录而牺牲 checkpoint、原子发布、恢复或取消清理。
- 不在完整 A/B 之前删除旧 writer、修改默认 chunks 或修改默认并发参数。
