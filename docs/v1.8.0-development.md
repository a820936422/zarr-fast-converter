# Fast NC Zarr v1.8.0 开发文档

- **目标版本**：v1.8.0
- **基线版本**：v1.7.9（开发中）
- **文档更新**：2026-08-18
- **关联文档**：[维护文档](MAINTENANCE.md)、[模块与运行指南](README.md)

本文档记录 v1.8.0 的后续待处理内容。v1.7.9 已完成的 Python 侧后端优化作为基线，剩余需要架构/Rust 改造或进一步验证的项统一列入 v1.8.0。

---

## 1. v1.7.9 已完成内容（基线）

- 版本提升至 1.7.9。
- 存储感知 worker/batch **初始值**（非硬上限），调优保留全范围 worker 扫描。
- `HardwareProfile`：存储顺序读/写带宽、随机 4K IOPS、NUMA 拓扑、P/E 核识别、缓存。
- `PerformanceModel`：候选耗时估算与排序（`FAST_NC_ZARR_PERF_MODEL=1` 启用）。
- 重分块存储感知初始值 + 全范围实测。
- `WorkerPool` 工具类。
- 文件亲和排序（HDD）。
- `OnlineController`：启发式规则、直写可观测性、保守 pending 主动调整。
- CPU affinity（`FAST_NC_ZARR_CPU_AFFINITY`）。
- PipelineFusion eligibility 标记。
- Python 测试 251 passed。

---

## 2. v1.8.0 目标

1. 把 v1.7.9 中“工具已就绪但未全路径接入”的优化真正接入转换/重采样/重分块执行路径。
2. 实现流水线单遍流式融合，降低中间 Zarr 写放大。
3. 扩展 native 能力，覆盖 int16 / HDF-EOS / 更多重采样方法。
4. 建立真实数据 scaling 基准并纳入发布门禁。

---

## 3. 待办清单

### 3.1 后端性能与调度

- [ ] **WorkerPool 全路径接入**
  - 将 `WorkerPool` 接入 `direct_write`、`resample`、`rechunk` 与 pipeline 阶段；
  - 解决“worker 初始化依赖输出路径”问题（将输出上下文改为按任务传递或按调用重置）；
  - 按 `memory_budget` 限制池大小，空闲时释放。
- [ ] **读写阶段分离（HDD 同设备）**
  - 源/输出同设备 HDD 时，降低读写磁头争用；
  - 在保持原子发布约束前提下，评估跨设备 staging/分批读写方案。
- [ ] **PipelineFusion 单遍流式执行**
  - 基于 `streaming_fusion_eligible` 标记实现真正的单遍流式；
  - 转换 worker 在内存中按目标 chunk 产出，直接进入重采样/重分块；
  - 保留 staging、原子发布、失败清理与 checkpoint 语义。
- [ ] **OnlineController 扩展到全部后端**
  - 接入 `run_resample` 与 pipeline 阶段；
  - 从“pending 调整”扩展到 worker/batch/压缩的实际调整；
  - 所有调整写入 manifest/events。
- [x] **PerformanceModel 默认启用与剪枝**
  - 候选排序/剪枝已从 `FAST_NC_ZARR_PERF_MODEL=1` 改为默认启用；`FAST_NC_ZARR_PERF_MODEL=0/off/false` 可关闭（调试用）。
  - 有缓存 HardwareProfile 时按估算耗时排序，短调参预算优先评估更优候选；
  - 剪枝保留全部 1..worker-ceiling worker 扫描候选，仅压缩/布局/batch 候选按估算排序截断；
  - 新增 `keep_full_worker_sweep` 与 `performance_model_enabled` 单测（`tests/test_performance_model.py` 8 passed）。
- [ ] **HardwareProfile 调度集成**
  - 将 NUMA/P/E 核信息用于 worker 绑核与调度；
  - 将存储微基准用于 HDD/SSD 初始值动态调整（例如 HDD 实测带宽高时提高初始 worker）。

## 4. 验收标准（v1.8.0 完成定义）

1. WorkerPool 在转换/重采样/重分块/pipeline 中实际复用，短任务与多阶段开销下降。
2. 源/输出同设备 HDD 场景有可测的读写阶段分离收益。
3. Pipeline 在 eligible 路径实现单遍流式，`write_amplification` 下降。
4. OnlineController 在主要后端实际调整 worker/batch/压缩并记录事件。
5. native 至少覆盖 int16 或 HDF-EOS 之一，并通过真实数据 parity。
6. 真实数据 scaling 基准纳入发布门禁。
7. 全量回归保持绿色，文档同步完成。
