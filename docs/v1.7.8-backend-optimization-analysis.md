## 0. 结论摘要

当前后端已经具备较好的“硬件自适应”基础：能检测 CPU/内存/cgroup/存储介质，并基于样本实测做 plan 调优。但从“在不同硬件上都能把当前硬件性能全部发挥出来”的标准看，仍有明显优化空间：

1. **并发模型偏“CPU 数量驱动”，对存储介质/IO 特性不敏感**：大文件在 HDD 上也会默认尝试接近全部 CPU 核数的 worker，容易造成磁盘寻道抖动。
2. **调优是“离线样本式”的，缺少运行期反馈**：选定 plan 后不会根据实际吞吐、CPU 利用率、磁盘队列、内存压力做动态调整。
3. **进程池按操作反复创建销毁**：spawn 开销在短任务/多阶段 pipeline 中不可忽略。
4. **重采样存在线程嵌套过订阅风险**：`space_workers × compute_workers` 未全局约束到逻辑核数。
5. **pipeline 仍是“转换→重采样→重分块”多遍落盘**：中间 Zarr 全量写读造成写放大。
6. **内存预算使用固定 512 MiB/worker 估算**，与实际 chunk/ESMF 工作集有偏差。

建议按“**硬件画像 + 性能模型 + 在线反馈 + 存储感知调度 + 流水线融合**”的方向重构后端调度层，分阶段落地。

### 0.1 已落地代码优化（P0 子集）

- ✅ **存储感知 worker/batch 默认值**（`src/fast_nc_zarr/planner.py`）：
  - 新增 `storage_aware_worker_limit()`：HDD/network 自动计划降低 worker 上限，SSD/unknown 保持 CPU/内存上限；
  - `initial_plan`（含 Dask 回退）在自动模式下应用该上限；`candidate_plans`/`fixed_layout_candidate_plans` 仍保留完整安全 worker 扫描，让调优自行发现最优并发；
  - HDD 大文件默认 `task_batch=4`，提高同一 worker 连续处理空间块的局部性；
  - 实测：FLUXSATv2（HDD、源+输出同设备）初始计划由 `workers=12, batch=1` 变为 `workers=2, batch=4`。
- ✅ **重采样全局线程预算**（`src/fast_nc_zarr/resampling/autotune.py`）：
  - `resolve_auto_space_workers()` 现在保证 `space_workers × compute_workers ≤ effective_cpus`，避免线程过订阅。
- ✅ **新增单测**：`tests/test_backend_adaptive.py`（6 个用例），全量 Python 测试 `232 passed`。
- ⏳ 尚未实施：运行期反馈控制器、长驻 worker 池、文件亲和调度、流水线融合、硬件微基准与性能模型、NUMA/affinity。

## 1. 本轮测试结果对性能的启示

### 1.1 已获得的事实

- 测试机：6 物理核 / 12 逻辑核，31 GiB 内存，源数据和输出都在同一块 HDD（`rotational=True`，`medium=hdd`），临时目录在 `tmpfs`。
- `EffectiveResourceBudget` 正确识别：`cpu_effective=12`、`worker_ceiling=12`、`memory_budget≈27 GiB`、`same_device_roles=['source+output']`。
- L0/L1 为正确性测试，固定单 worker、32×32 窗口、≤2 时间步：
  - FLUXSAT 单文件 GPP：0.119 s / 8 KiB 逻辑量；
  - GLASS 两文件 evi：0.264 s / 4 KiB 逻辑量；
  - FLUXSAT 两月拼接：2.485 s / 236 KiB 逻辑量。
- `validate-raw` 全树验证：1240 文件通过，FLUXSAT 使用 6 个进程检查 228 个大文件，GLASS 使用 6 个进程检查 1012 个小文件。

### 1.2 启示

1. 当前测试没有暴露“最大性能”，因为样本太小且固定单 worker；它验证的是**正确性和资源探测**。
2. 真实全量/中等规模性能需要专门的 scaling 测试（workers 1→12、不同 chunk、不同 codec、HDD/SSD 对比）。
3. 已经检测到“源+输出同设备 HDD”，但当前 plan 没有利用该信息做并发限制或读/写阶段分离，这是最直接的优化点。
4. `validate-raw` 对 228 个大文件用 6 进程说明系统能支撑中等并发；但并发是否最优没有被度量。

## 2. 当前后端处理逻辑盘点

| 模块 | 现状 |
|---|---|
| 资源探测 `system.py` | 检测物理/逻辑核、affinity、cgroup CPU/内存、FD 限制、WSL、存储介质（HDD/SSD/network）、源/临时/输出同设备关系 |
| worker 预算 `EffectiveResourceBudget.worker_ceiling` | 默认按 `512 MiB / worker` 估算内存上限，结合 CPU/FD 求最小值；`requested` 作为硬上限 |
| 转换规划 `planner.py` | 按 `workload_kind`（many-small-files / large-files / balanced）选择 `file` / `chunk` / `dask` 策略，生成 workers×chunks×codecs 候选 |
| 转换调优 `benchmark.py` | 用代表性小样本（分层 temporal samples）实测候选 plan 的吞吐/压缩率/RSS，预算内选优 |
| 直接写入 `writer.py` | 进程池 + 有界 pending + per-worker 源文件 LRU cache + batch 写入；单 worker 走串行 |
| Dask 回退 `engine.py` | `xr.open_mfdataset` + dask `processes` 调度，用于不兼容直接写入的变量 |
| 重采样 `resampling/autotune.py` | 基于内存模型自动选 `space_workers` / `time_block` / `tile_size`；每个空间 worker 内部再用 Dask threads 做 `compute_workers` 计算 |
| 重分块 `rechunking/engine.py` | 两阶段 worker 调优 + compression 调优 |
| pipeline `pipeline/engine.py` | 顺序执行 conversion→resampling→finalization，每阶段 staging + 校验 + manifest/checkpoint |

## 3. 可优化空间

### 3.1 存储介质感知不足（最优先）

- `initial_plan` 对 `large-files` 直接 `workers = cpus`，只把“源和目标同设备”作为 benchmark context，不参与静态限制。
- HDD 的随机读并发收益很低，过高并发反而增加寻道；SSD/NVMe 则相反。
- 设计应把存储介质、设备角色、实测带宽纳入 worker/chunk/task_batch 的默认决策。

### 3.2 缺少运行期反馈控制

- 当前 `tune` 只在开始前用小样本选 plan，正式写入期间不根据实时吞吐/CPU/磁盘队列调整。
- 机器负载可能在任务中途变化（其他进程、热降频、IO 抢占），固定 plan 无法自适应。
- 需要轻量 telemetry + 控制器：若吞吐停滞而 CPU 低，则降 worker 或增大 chunk；若 CPU 打满而磁盘空闲，则提高压缩或换更小 chunk；若 RSS 接近上限，则降并发/启用 memmap。

### 3.3 进程池生命周期与 spawn 开销

- `direct_write`、`resample`、`rechunk` 各自创建 `ProcessPoolExecutor`，任务结束后销毁。
- 对短任务和 pipeline 多阶段，spawn（重新导入 xarray/dask/zarr 等）开销占比高。
- 设计长驻 worker 池（或 fork server / persistent workers），跨任务、跨 pipeline 阶段复用，并缓存源文件句柄。

### 3.4 重采样线程过订阅

- `resolve_auto_space_workers` 只按内存估算空间 worker 数，`compute_workers` 是每个空间 worker 内部线程数。
- 没有约束 `space_workers × compute_workers ≤ logical_cpus`，可能造成线程切换/内存带宽争用。
- 需要全局 CPU 预算：把“进程数 × 每进程线程数”统一纳入调度。

### 3.5 内存模型偏固定

- 转换 worker 内存按固定 512 MiB 估算；实际峰值与 chunk 大小、dtype、变换、压缩有关。
- 重采样已用更细的 ESMF baseline + tile 估算，但转换/重分块仍较粗。
- 应把调优阶段实测的 `peak_rss` 反馈到 worker 上限计算，形成“测量→校准”闭环。

### 3.6 HDD 顺序读未最大化

- 当前任务顺序是 time-major 再 spatial；多个 worker 同时读同一大文件的不同空间窗口会在 HDD 上产生随机寻道。
- 可做“文件亲和调度”：同一 worker 尽量连续处理同一文件/相邻时间片，减少并发随机读；或引入 read-ahead/prefetch。
- 当源与输出同设备时，可错开读写阶段（先批量读入内存/tmp，再批量写输出），减少磁头乒乓。

### 3.7 Pipeline 写放大

- 当前 pipeline 是转换→重采样→重分块多遍落盘，中间 Zarr 全量写读。
- 对可直接写入的变量，可设计“流式融合”：转换阶段按目标 chunk 产出，重采样/重分块在同一 worker 内消费，减少中间 store 的物理写读。
- 必须保留 staging、校验、checkpoint 与失败恢复语义；融合仅在没有 checkpoint 依赖或可安全重建时启用。

### 3.8 压缩策略未与存储速度联动

- HDD 慢、CPU 有富余时，更高压缩等级可以减少落盘字节，整体更快；NVMe 快时，低压缩/不压缩可能更优。
- 当前 tune 的 `balanced` 目标没有把存储带宽和 CPU 成本联合建模。
- 应引入“存储带宽 vs CPU 压缩成本”的成本函数，按硬件选择压缩 codec/level/shuffle。

### 3.9 Dask 回退路径可优化

- `_dask_write` 使用 `xr.open_mfdataset(..., parallel=False, chunks={})` 对多文件做全量元数据合并，大目录下内存和启动开销高。
- 对不兼容直接写入的变量，可考虑按文件/时间分块流式处理，而不是构造整图再 compute。
- 也可在 Python 侧用更轻量的分块 reader 替代 open_mfdataset。

### 3.10 硬件拓扑利用不足

- 没有 NUMA 感知、CPU affinity 设置、L2/L3 cache 大小探测。
- 对多路/大小核（P-core/E-core）机器，默认“12 个 worker”可能把任务派到低性能核。
- 设计应读取 CPU 拓扑，区分性能核/能效核，并支持 worker 绑核。

## 4. 自适应后端设计

### 4.1 设计目标

> 让同一套后端在 HDD 笔记本、NVMe 工作站、内存受限容器、多路服务器上都能自动逼近“当前硬件条件下的最优吞吐”，同时保持正确性、可恢复性和可观测性。

### 4.2 核心架构：硬件画像 → 工作负载分类 → 性能模型 → 候选生成 → 样本调优 → 在线反馈

```text
+------------------+     +------------------+     +------------------+
| Hardware Profiler| --> | Workload Classifier| --> | Performance Model|
| CPU/NUMA/mem/disk|     | file size/mode/var|     | cost estimation |
+------------------+     +------------------+     +--------+---------+
                                                           |
                                                           v
+------------------+     +------------------+     +------------------+
| Online Controller| <-- | Sample Tuner     | <-- | Candidate Planner|
| telemetry adjust |     | benchmark select |     | workers/chunks/ |
+------------------+     +------------------+     | codecs/batch    |
                                                  +------------------+
```

#### 4.2.1 硬件画像（Hardware Profile）

在现有 `RuntimeResourceSnapshot` 基础上扩展：

- CPU：物理核/逻辑核、affinity/cgroup、NUMA 节点、P/E 核分组、L2/L3 cache 大小。
- 内存：总量/可用/cgroup、内存带宽粗测（可选）。
- 存储：介质、文件系统、**实测顺序读/写带宽、随机 4K IOPS、磁盘队列深度**、是否同设备。
- 系统负载：启动时 CPU/IO 占用，用于保守默认值。
- 持久化缓存：相同路径/设备组合复用 profile，避免每次启动都做 IO 微基准。

#### 4.2.2 工作负载分类

- 文件数/大小分布、总字节、每个文件时间点数、source mode、变量 dtype/数量、是否含变换、是否重采样/重分块。
- 输出目标：Zarr 直接写、重采样、重分块、pipeline。
- 预估计算密度（CPU-bound） vs IO 密度（I/O-bound）。

#### 4.2.3 性能模型

为每个候选 plan 估计：

```text
T ≈ T_spawn + T_read + T_transform + T_compress + T_write + T_validate
```

其中：

- `T_read` 由源存储带宽、窗口大小、顺序/随机访问模式决定；
- `T_compress` 由 CPU 核数、codec/level、数据可压缩性决定；
- `T_write` 由目标存储带宽、chunk 大小、staging 设备决定；
- `T_spawn` 由 worker 数、进程池生命周期决定。

模型不要求绝对精确，目标是**剪枝候选空间**，让样本调优聚焦在少数有希望的 plan。

#### 4.2.4 候选生成（存储感知）

- HDD：worker 数默认 `min(2~4, cpu)`，chunk 更大（减少 seek），task_batch 提高（顺序读），优先 file-affinity。
- SSD：worker 数 `min(8~12, cpu)`，chunk 适中，高并发。
- NVMe：worker 数 `≈ cpu`，chunk 可更小，低压缩甚至 none（若 CPU 是瓶颈）。
- 源/输出同设备：限制总并发，或把 staging 放到不同设备（如 tmpfs/SSD）并启用“读写阶段分离”。
- 内存受限：按实测 RSS 校准 worker 上限，启用 memmap spill。

#### 4.2.5 样本调优

保留现有 `benchmark.tune` 分层样本思路，但：

- 候选集由性能模型剪枝；
- 采样窗口大小根据存储带宽动态决定（HDD 上避免过小样本导致 cache 假象）；
- 记录每个候选的 `read_throughput`、`write_throughput`、`cpu_util`、`peak_rss`，用于校准模型。

#### 4.2.6 在线反馈控制器

正式执行期间以 1–5 秒粒度采样：

- `achieved_throughput`、`cpu%`、`rss`、`disk_queue/await`；
- 若吞吐连续停滞且 `cpu < 60%`：可能 IO 瓶颈 → 降并发 / 增 chunk / 打开 read-ahead；
- 若 `cpu > 90%` 且磁盘空闲：可能 CPU 瓶颈 → 降压缩等级 / 减 worker（避免上下文切换）/ 增大 batch；
- 若 `rss` 接近预算：降 worker / 减小 time_block / 启用 memmap；
- 每次调整写入 manifest/events，保证可复现和审计。

#### 4.2.7 进程/线程模型

- 全局 CPU 预算：`processes × threads_per_process ≤ effective_cpus`。
- 转换/重分块默认 `threads_per_process=1`，纯进程并行；
- 重采样强制 `space_workers × compute_workers ≤ effective_cpus`，并记录实际预算；
- 长驻 worker 池：跨任务复用，避免反复 spawn；
- 可选 NUMA/CPU affinity 绑定。

#### 4.2.8 流水线融合

- 仅对 `direct_compatible` 且无 checkpoint 需求的路径启用；
- 转换 worker 在内存中按目标 chunk 产出，直接交给重采样/重分块逻辑；
- 保留 staging 原子发布和失败清理；融合时记录 `write_amplification` 下降量。

#### 4.2.9 后端选择

- 维持 capability matrix + `backend=auto` 显式 fallback；
- 扩大 native 覆盖（int16、HDF-EOS、更多重采样方法）以降低 Python 开销；
- native 路径同样接入资源预算与在线反馈。

#### 4.2.10 配置与可观测性

- 提供 `performance-mode` 预设：`balanced` / `max-throughput` / `low-memory` / `hdd-safe` / `ssd-max`；
- manifest 增加 `hardware_profile`、`performance_model`、`online_adjustments`；
- 暴露 `pixi run benchmark-hardware-profile` 等诊断命令。

## 6. 风险与兼容性

- **不要过度工程**：在线控制器默认保守，失败时回退到当前确定性的初始 plan。
- **HDD 行为差异大**：默认值要保守，并以实测微基准为准。
- **流水线融合可能破坏 checkpoint/恢复**：只对可安全融合的路径开启，保留 staging 和 manifest。
- **在线调整会导致非确定性**：所有调整必须写入事件/manifest，便于复现。
- **长驻 worker 池增加常驻内存**：需按 `memory_budget` 限制池大小，空闲时释放。
